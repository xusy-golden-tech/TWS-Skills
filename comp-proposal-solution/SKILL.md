# 方案设计

## 核心原则

**方案不是功能清单，是"怎么做"的完整回答。**

客户不需要你复述他要什么（需求澄清已经做了），他要你告诉他：怎么做、分几步、为什么这样做、风险在哪。

## 前置输入

从需求摘要中获取：

- 显性需求和潜在需求（设计必须覆盖的范围）
- 范围边界（本次做什么不做什么——不要越界）
- 约束条件（时间/预算/技术栈/合规——方案在这个边界内做）

如果需求摘要缺少以上任何一项，不要硬设计——返回主 agent，列明缺失项。

## 子能力

### A. 架构设计

不是画张图就完了。架构设计的本质是**把系统拆成可理解、可独立描述、可独立估价的块**。

#### 确定架构风格

```
根据项目类型选择架构模式（不要默认选微服务）：

| 项目特征 | 推荐风格 | 原因 |
|---------|---------|------|
| 单团队、1-3 月、功能 ≤ 5 个核心模块 | 单体或模块化单体 | 微服务的复杂度和项目规模不匹配 |
| 多团队、多子系统、需独立部署 | 微服务 | 独立部署和团队自治有价值 |
| 数据流密集、批处理 + 实时 | 管道/事件驱动 | 数据处理是核心复杂度 |
| 纯前端展示、后端简单 CRUD | 前后端分离即可 | 不要过度设计 |

选择理由必须绑定项目约束——"大公司用微服务所以我们也用"不是理由。
```

**为什么先定架构风格：** 风格定了，模块划分和技术选型才有方向。否则先选技术后定架构 = 用锤子找钉子。

#### 画出架构图

```
用 mermaid 或 ASCII 画出系统整体结构：

必须包含：
- 系统边界（哪些是你做的，哪些是外部系统）
- 主要组件和它们的通信方式（HTTP / 消息队列 / 共享数据库）
- 数据流方向（数据从哪来到哪去）

可选（如果项目涉及）：
- 部署拓扑（几台机器、负载均衡、容灾）
- 外部依赖（第三方 API、现有系统）
```

**为什么必须有图：** 文字描述的架构 = 每个人理解不一样的架构。一张图 = 对齐所有人。

### B. 技术选型

每个技术决策必须有可辩护的理由：

```
选型规则：
1. 每个维度只选一项（不要写"Java 或 Go 都可以"——那是没做决策）
2. 理由绑定项目约束，不是行业宣传语
3. 备选方案是降级路径（万一选了不能用，还有什么可选）

| 维度 | 选型 | 理由（绑约束） | 备选 |
|------|------|-------------|------|
| 后端语言 | Go | 客户要求高并发低延迟（需求 R5），Go 的并发模型原生支持 | Java（客户团队也接受） |
| 前端框架 | React | 团队现有经验 + 需要复杂交互 | Vue |
| 数据库 | PostgreSQL | 需要复杂查询 + 事务 + JSONB 存储非结构化数据 | MySQL |
| 部署 | Docker Compose（单机） | 客户只有一台服务器，K8s 过重 | 裸机部署 |
```

常见选型陷阱：

```
❌ "用 React 因为它流行" — 流行 ≠ 适合
❌ "用微服务因为大家都在用" — 微服务解决组织问题，不解决技术问题
❌ "用 MongoDB 因为灵活" — "灵活" = "我不知道 schema 长什么样" = 你在推卸设计责任
❌ 技术栈全是新潮工具 — 客户的维护团队会骂你
```

**如果把不准用什么**：在假设声明中标注"技术选型基于常规实践，建议 POC 验证"。

### C. 模块拆解

把系统拆成若干个可独立描述的模块：

```
拆解原则（按优先级排）：
1. 每个模块有单一职责——一个模块只做一件事
2. 模块间依赖显式声明——A 依赖 B，不要藏着
3. 模块边界清晰——给一个模块的人不需要读懂其他模块的内部实现
4. 标注哪些可以并行开发——这是交付排期的输入
5. 模块数 = 3-8 个为宜。少于 3 个可能没拆够，多于 8 个可能拆过头

每个模块输出：
| 模块 | 职责 | 对外接口 | 依赖 | 复杂度 | 可并行 |
|------|------|---------|------|--------|--------|
| 用户中心 | 注册/登录/权限/个人资料 | REST API | 无 | 中 | 是 |
| 订单 | 创建/支付/状态流转 | REST API + 回调 | 用户中心, 支付网关 | 高 | 否(依赖用户中心) |
```

**为什么这个结构：** 模块拆解直接决定交付节奏——每个模块是一个独立的交付单元。模块边界不清 = 交付重叠或遗漏。复杂度标注用于评估技术风险，不用于人天估算。

### D. 交付节奏

把模块按依赖关系排成阶段：

```
排程原则：
1. 先做无依赖的模块（基础模块）
2. 再做依赖已就绪的模块
3. 每个阶段有一个可演示的产出

| 阶段 | 时间 | 模块 | 交付物 | 验收标准 |
|------|------|------|--------|---------|
| 1 | 第 1-2 周 | 用户中心 | 可注册/登录/权限管理 | 能跑通注册→登录→访问受保护页面 |
| 2 | 第 2-3 周 | 订单 + 支付 | 可下单/支付/查看订单 | 能跑通货→下单→支付→看订单 |
```

验收标准的写法：
```
✅ "用户可从首页注册→验证邮箱→登录→访问 Dashboard"
❌ "用户功能基本完成"
```

**为什么验收标准必须可验证：** 这是你和客户对齐的唯一依据。"基本完成" = 你说完成了客户说没完成 = 扯皮。

### E. 风险识别与假设声明

#### 风险

只写本项目特有的风险。通用项（"人员离职""需求变更"）不写，因为没人会根据通用风险改方案：

```
风险识别方法（Pre-Mortem）：
假设项目失败了，最可能的 3 个原因是什么？

然后反过来检查：你的方案里有针对这些原因的措施吗？

| 风险 | 可能性 | 影响 | 缓解措施 | 残留风险（缓解后还剩什么） |
|------|--------|------|---------|------------------------|
| 支付网关对接文档不全 | 高 | 中 | 提前申请沙箱环境验证 | 生产环境参数可能不同 |
| 客户提供数据格式与预期不符 | 中 | 高 | 在阶段 1 先要一份样本验证 | 如果格式完全不同需调整设计 |
```

**为什么写残留风险：** 缓解不是消除——让决策者知道"我们做了 X 但仍然有 Y 的可能性"。

#### 假设

列出所有支撑方案但未经验证的假设。假设越多 = 方案的可信度越低 = 报价时需要更多缓冲：

```
假设必须具体：
✅ "假设第三方 API 支持批量查询（文档说支持但未实测）→ 不成立则需逐条查询，性能降 80%"
❌ "假设第三方 API 稳定" — 太笼统

如果假设超过 5 个，说明你对需求的理解不够深，或者这个项目本身高度不确定。
```

## 决策判断

以下情况不要出方案，返回主 agent：

```
□ 需求摘要中的约束互相矛盾且不可调和
□ 关键约束导致所有可行方案都被排除（"必须 1 个月完成 100 个人月的工作"）
□ 技术栈约束与功能需求冲突（"必须用 Excel 做实时协作"）
```

以下情况标注为高风险方案：

```
□ 需要新技术但团队或客户没有相关经验
□ 依赖未经验证的第三方服务
□ 交付节奏有不可压缩的刚性依赖（"必须先等客户完成 X"）
□ 假设超过了 5 个
```

## 常见失败模式

| 表现 | 根本问题 | 正确做法 |
|------|---------|---------|
| 方案全是功能罗列 | 把需求复述当设计 | 回答"怎么做"而非"做什么" |
| 技术选型无理由 | 抄常用组合 | 每个选型绑定项目约束 |
| 架构图 = 一个方框写"系统" | 没做架构分解 | 拆出组件和数据流 |
| 模块拆得过细（15+）或过粗（< 3） | 没掌握粒度 | 以能否独立估价为标准 |
| 里程碑验收标准="基本完成" | 不可验证 | 用客户能看懂的操作描述 |
| 风险 = 通用列表复制粘贴 | 没做项目特异的 Pre-Mortem | 问自己：这个项目死于什么 |

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| "这个架构很标准，不用画图" | 没图的架构 = 每个人理解都不一样 |
| "技术选型就用常用的" | 常见的未必适合这个项目的约束。你是在偷懒 |
| "交付节奏到时候再说" | 没有节奏的报价是瞎报。交付节奏 = 报价的骨架 |
| "风险都差不多，复制一下" | 通用风险 = 没用的风险。没人看也不会有人据此行动 |
| "假设太多了不好看" | 隐藏的假设 = 定时炸弹。宁可列 5 个，不要藏 1 个 |
| "模块拆得太细报价会显高" | 报低 = 后面你自己填坑。拆细 = 每个数字有出处 |
