# 根因分析

## 核心原则

**找到源头，而不是找到出现症状的地方。**

## Step 0: 图中查找调用链

在手动追踪之前，先用代码图获取调用链——一条命令得到从入口到报错点的完整路径，每步标注文件:行号。

**前置检查：**

```
0.0 tws-graph --version 2>&1
    → 成功 → 继续 0.1
    → 失败（"command not found" 等）→ Bash: pip install -e tws-graph/ 2>&1
    → 安装成功 → 继续 0.1
    → 安装失败（找不到 tws-graph/ 目录或 pip 报错）→ 「tws-graph 不可用，退回到手动 grep/read 追踪」
```

```
0.1 tws-graph index              ← 确保索引是最新的

0.2 如果知道入口和报错点：
    tws-graph trace <入口> <报错点>
    → 完整调用链，每一步标注文件:行号
    → 直接跳到下面步骤 1，沿 trace 输出逐层读代码

0.3 如果只知道报错点不知道入口：
    tws-graph calls <报错点> --inbound --depth 3
    → 找到所有上游调用者，识别可能的入口
    → 然后对每个可能的入口执行 tws-graph trace <入口> <报错点>
```

**静态分析边界：**

```
如果 tws-graph trace 返回 "未找到路径"：
    → 可能是动态调度、闭包、回调、反射
    → 标注 provenance=heuristic
    → agent 退回到手动 grep + read 追踪
    → 这不计入 3 次迭代上限（这是工具能力边界，不是 agent 能力问题）
```

## The Gate Function

```
1. 追踪：沿 trace 输出的调用链逐层检查（每层读代码、查日志）
2. 定位：找到第一个出错的位置（文件:行号）
3. 分析：为什么会出错（逻辑错？数据错？外部依赖错？）
4. 评估：影响范围（通过 tws-graph calls --inbound --depth 1 确认所有消费者）
5. 输出：根因 + 影响
```

## 时间盒

```
如果在定位阶段迭代超过 3 次仍未确认根因：
→ STOP
→ 整理所有假设和证据
→ 输出排查报告（已排除什么、还剩什么可能性）
→ 提交给开发者判断方向

限制：最多 3 次假设验证循环
超过 → 上报，不是继续猜。

如果 tws-graph trace 无法找到路径：
→ 这是静态分析工具的边界（动态调度、闭包、回调、反射）
→ agent 退回到手动 grep + read 追踪
→ 不计入 3 次迭代上限
```

## Output Format

```
- 根因：{文件:行号} {具体原因}
- 触发条件：{什么场景下出现}
- 影响：{哪些功能/用户}
- 建议修复：{修改方向}
```

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| 「这个问题我见过」 | 看过类似的 ≠ 就是同一个原因。追踪确认再下结论 |
| 「肯定是 XX 的问题」 | 「肯定」= 还没查。查完再说话 |
| 「先改这里试试」 | 试 = 没定位到根因。定位清楚了再改 |
| 「trace 没找到路径 = 无依赖」 | trace 有静态分析边界。用 grep 再确认 |
| 「手动追踪也一样，不查图了」 | tws-graph trace 一秒给出完整链，手动要好多轮。先查图 |
