# 记录架构决策

## 核心原则

**架构决策由人类写入，agent 只提供素材。**

本 skill 是人类项目经理的工具，不是 agent 自动触发的流程。

---

## 输入

项目经理提供 agent 们上报的决策报告（原始文本），格式不限。

---

## 步骤

### ① 格式化

将原始报告整理为固定格式：

```markdown
### {决策标题}

- **时间**：YYYY-MM-DD
- **背景**：{为什么需要做这个决策}
- **决定**：{选了什么方案}
- **排除**：{排除了什么方案，为什么}
- **影响**：{影响哪些模块 / 后续开发需要注意什么}
- **来源**：{哪个功能的设计书或流程产生的}
```

每条决策一个 `###` 块，按时间倒序排列（最新的在最前面）。

### ② 一致性检查

派子 agent 检查待写入的决策与 `.tws/architecture-decisions.md` 中已有决策的一致性：

```
子 agent 收到：
  - 待写入的决策列表（格式化后）
  - .tws/architecture-decisions.md 的完整内容

检查项：
  □ 重复：是否有已存在的决策说的是同一件事？
    → 标注：「与 {已有决策标题} 重复，建议合并或补充」

  □ 矛盾：新决策是否与已有决策冲突？
    → 标注：「与 {已有决策标题} 矛盾——{冲突点}，请确认以哪个为准」

  □ 过时：新决策是否使某个已有决策过时？
    → 标注：「{已有决策标题} 可能已被新决策取代，建议标记 superseded」

子 agent 只报告发现，不做修改决策。
```

### ③ 输出确认

将格式化后的决策列表 + 一致性检查报告一起输出给项目经理：

```
## 待写入的架构决策

{格式化后的决策}

## 一致性检查

- 重复：{发现或"无"}
- 矛盾：{发现或"无"}
- 过时：{发现或"无"}

确认写入？
→ 全部写入 / 跳过标记项 / 选择写入 / 取消
```

### ④ 写入

按项目经理确认结果写入 `.tws/architecture-decisions.md`：

```
写入规则：
- 新决策插入文件顶部（最新的在前）
- 被取代的决策不删除，在标题后追加 [superseded by {新决策标题}]
- 矛盾的决策不自动修改，由项目经理决定是否修改已有条目
```

### ⑤ 文件维护

```
文件超过 ~50 行（约 15 条活跃决策）时提醒：
「architecture-decisions.md 已有 {N} 条活跃决策，建议整理：
  - 标记为 superseded 的可以归档
  - 只跟已归档功能相关的可以移入对应设计书
  是否需要整理？」
```

---

## 读取方式

以下 skill 读取 `architecture-decisions.md` 时，按固定格式解析：

```
design-doc       → 写设计书前，检查是否有相关决策，避免矛盾
impact-assessment → 评估影响时，参考历史决策背景
design-sync      → 判断是否需要上报时，检查是否已被记录

格式保证：
  每条决策以 ### 标题开头
  包含 时间 / 背景 / 决定 / 排除 / 影响 / 来源 六个字段
  新的在前，superseded 的有标记

读取时不需要全量加载，按 ### 分块，只读与当前任务相关的决策。
```

---

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| 「这个决策不重要，不用记录」 | 重不重要由项目经理判断，agent 只负责上报 |
| 「之前好像记过类似的」 | 跑一致性检查确认，不要靠记忆 |
| 「格式随便写一下」 | 格式不统一 = 后续 agent 无法可靠解析 |
| 「自动写入就好，不用确认」 | 架构决策影响全局，必须人类审核 |
