# 测试

## 核心原则

**「看起来没问题」不是测试结果。测试输出才是。**

测试分两个阶段，由调用方（flow skill）指定当前处于哪个阶段：

### 设计阶段（编码前）

编码开始前，基于设计书（而非代码）推导测试用例：

```
基于设计书，逐条验收标准/接口契约推导：

1. 正常路径：每个接口/函数的正常输入和预期输出
2. 边界值：null、空字符串、空集合、零值、极限值
3. 异常路径：错误输入、超时、资源不足
4. 组合场景：多个条件叠加时的行为

产出：测试用例清单 + 测试脚本（此时运行应失败——代码尚未实现）
```

设计阶段的测试从需求推导，不从代码推导。测试用例编写者不应看到实现代码——只看到设计书。

### 执行阶段（编码后）

编码完成后，运行已在设计阶段编写好的测试，验证代码是否正确实现了设计。详见下方"The Gate Function"。

## Step 0: 图中确认回归范围

跑测试之前，先用代码图确认改动的影响范围，确保回归测试覆盖所有受影响的模块。

**必须操作：** 通过 Skill 工具加载 `found-tws-graph-usage`（Skill(skill: "found-tws-graph-usage")），按其中指引完成前置检查和以下查询：

```
1. tws-graph --version              ← 检查可用性（不可用则 pip install -e tws-graph/）

2. tws-graph impact <修改的符号> --depth 2  ← 查哪些模块依赖了被修改的符号
   → 这些模块的测试必须纳入回归范围

3. tws-graph calls <修改的符号> --inbound    ← 确认所有调用者都被回归覆盖
```

错误处理详见 `found-tws-graph-usage`。图返回空时标注 provenance=heuristic，退回到 Grep + Read 手动追踪。

## The Gate Function — 执行阶段

```
AFTER implementation, BEFORE claiming completion:

1. RUN: 所有相关测试（在设计阶段已编写，现在验证通过）
2. READ: 完整输出，确认 0 failures
3. CHECK: 边界条件
   □ 正常路径
   □ 空值/异常值
   □ 极限/边界值
   □ 错误输入
4. ONLY THEN: 标记测试通过
```

按 project-map.md 中的技术栈加载对应的领域测试 skill（如有）：`comp-backend-test`、`comp-frontend-test` 等。无匹配时使用本通用 skill。

## 回归验证

```
除了测试新增功能外，必须确认现有功能未被破坏：

□ 改动了哪些模块？
□ 这些模块的已有测试都跑了吗？
□ 依赖这些模块的其他模块测试跑了吗？
□ 全部通过 → 确认无破坏
□ 有失败 → 判断是预期行为变化还是真正的问题

「改 A 没测 B」是回归测试最常见的遗漏。
改动涉及的模块 + 依赖该模块的模块，都必须重跑测试。
```

## 测试失败：先分类再行动

测试执行阶段出现失败时，**禁止直接修测试或修代码**。必须先归类失败原因，再决定方向。

### 判定流程

```
测试失败
   ↓
① 这个测试的期望值与设计书一致吗？
   ├─ 一致 → 实现代码有问题 → 回到编码阶段，修复代码（测试不动）
   └─ 不一致 → ②
                ↓
② 设计书本身没说清楚或有遗漏吗？
   ├─ 是 → 先更新设计书，再决定改代码还是改测试
   └─ 否 → 测试代码写错了，修正测试，记录原因和依据
```

### 判定原则

- **测试代码享有更高权威性**——测试是从设计书推导的，改测试等于改验收标准
- 改测试之前必须回答：「设计书的哪一条说明这个测试期望是错的？」
- 答不上来 → 不能改测试，回去改代码
- 代码和测试都没错但设计书有歧义 → 先补设计书，再决策

### 禁止行为

| 禁止 | 为什么 |
|------|--------|
| 测试没过就直接改测试期望值 | 等于把验收标准改掉了 |
| 「测试写得太严格了，放宽一点」 | 严格程度是设计书定的，不是实现定的 |
| 「这个 case 实际跑不到，删掉」 | 删测试 = 删验收标准，留下隐藏 bug |
| 改代码时顺手改测试让它通过 | 无法区分是代码对了还是测试被污染了 |
| 改了测试但不记录原因 | 下次审查看不出设计意图是否被修改过 |

### 重试上限

分类完成后，按以下策略处理（重试次数在测试规约文件中配置，路径见 `.tws/project-map.md`）：

```
default_retry_limit = 3

第 1 次失败 → 归类，判定方向，修复后再跑
第 2 次失败 → 检查修复方向是否正确，换方案
第 N 次失败（N = retry_limit）→ 停止，上报开发者：
  - 哪些测试失败
  - 每次的判定结论（代码错 / 测试错 / 设计书遗漏）
  - 已尝试的修复方案和结果

限制：
- 同一任务最多重试 retry_limit 次
- 超过 → 标记为「阻塞」，上报开发者决策
- 不隐藏失败，不跳过，不降级
- 环境问题 → 走 found-environment-gov，不计入重试次数
- 只改测试代码的重试不计入修复次数——改了测试意味着绕过了问题
```

## 异常上报规则

```
测试失败时，即使看起来与本任务无关，也必须：

1. 记录：哪个测试？什么错误？完整输出？
2. 判断：之前是否通过？本次改代码引入的？
3. 上报：详情 + 判断
4. 等待：开发者决定修复、跳过、还是记入问题

Agent 没有权力替开发者过滤信息。
```

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| 「先看看能不能通过，不通过再修」 | 先修再跑。没想清楚就跑浪费次数 |
| 「这个失败不算，再跑一次」 | 跑 10 次过 1 次 = 不稳定。报上去 |
| 「换个环境就好了」 | 换环境要开发者同意，不是自己换 |
| 「重试了 3 次都不行，先跳过」 | 停下来上报，不是跳过 |
| 「测试没过，改一下测试就行」 | 先判断是测试错还是代码错。改测试 = 改验收标准 |
| 「实现已经写好了，测试太理想化」 | 测试的理想来自设计书。是代码没达到设计意图 |
