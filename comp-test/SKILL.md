# 测试验证

## 核心原则

**「看起来没问题」不是测试结果。测试输出才是。**

## The Gate Function

```
AFTER implementation, BEFORE claiming completion:

1. RUN: 所有相关测试（已有 + 新增）
2. READ: 完整输出，确认 0 failures
3. CHECK: 边界条件
   □ 正常路径
   □ 空值/异常值
   □ 极限/边界值
   □ 错误输入
4. ONLY THEN: 标记测试通过
```

## 领域测试 skill

按 project-map.md 中的技术栈加载对应的领域测试 skill（如有）：`comp-backend-test`、`comp-frontend-test` 等。无匹配时使用本通用 skill。

## 回归验证

```
除了测试新增功能外，必须确认现有功能未被破坏：

□ 改动了哪些模块？
□ 这些模块的已有测试都跑了吗？
□ 依赖这些模块的其他模块测试跑了吗？
□ 全部通过 → 确认无破坏
□ 有失败 → 判断是预期行为变化还是真正的问题

「改 A 没测 B」是回归测试最常见的遗漏。
改动涉及的模块 + 依赖该模块的模块，都必须重跑测试。
```

## 失败处理规则

测试失败后按以下策略处理（重试次数在测试规约文件中配置，路径见 `.tws/project-map.md`）：

```
default_retry_limit = 3  # 默认值，可在测试规约文件的 retry_limit 字段覆盖

第 1 次失败 → 修复后重跑
第 2 次失败 → 检查修复是否正确，换方案重试
第 N 次失败（N = retry_limit）→ 停止。上报开发者，说明已尝试的方案和结果

限制：
- 同一任务最多重试 retry_limit 次
- 超过 → 标记为「阻塞」，上报开发者决策
- 不隐藏失败，不跳过，不降级
- 环境问题 → 走 found-environment-gov，不计入重试次数
```

### 配置示例

在测试规约文件中（路径见 `.tws/project-map.md`）：

```markdown
## 重试配置
retry_limit: 5  # 覆盖默认的 3 次
```

## 异常上报规则

```
测试失败时，即使看起来与本任务无关，也必须：

1. 记录：哪个测试？什么错误？完整输出？
2. 判断：之前是否通过？本次改代码引入的？
3. 上报：详情 + 判断
4. 等待：开发者决定修复、跳过、还是记入问题

Agent 没有权力替开发者过滤信息。
```

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| 「先看看能不能通过，不通过再修」 | 先修再跑。没想清楚就跑浪费次数 |
| 「这个失败不算，再跑一次」 | 跑 10 次过 1 次 = 不稳定。报上去 |
| 「换个环境就好了」 | 换环境要开发者同意，不是自己换 |
| 「重试了 3 次都不行，先跳过」 | 停下来上报，不是跳过 |
