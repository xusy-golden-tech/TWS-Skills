# 报价评审

## 核心原则

**每个数字背后都有一个可以被质疑的假设。你的任务就是找出来，质疑它。**

报价评审不是复核算术——1+1 不会因为你审了变成 3。你审的是：凭什么这个模块 5 天？凭什么这项服务 ¥2000/月？项目的盈亏在估算偏差里，不在谈判桌上。

**为什么需要独立评审：** 报价是对方案的翻译。翻译可能出错——漏翻、多翻、估算偏差。报价者自己不容易发现，因为他刚做完估算，潜意识里已接受了自己的数字。

## 前置输入

- 方案文档（已锁定版本——报价应基于这个版本）
- 报价方案（待评审）

对照方案逐项验证——报价中的每个数字必须能追溯到方案中的某个设计决策。

## 子能力

### A. 依据质量检查

```
逐项检验报价中每个估算的依据：

| 模块/角色 | 人天 | 依据 | 依据质量 | 问题 |
|-----------|------|------|---------|------|
| 用户/后端 | 5 | 3 API + 权限中间件 | 好（具体可验证） | 无 |
| 报表/前端 | 8 | "中等复杂度" | 差（不可验证） | "中等"因人而异——你是按 3 个图表页面估的，还是 10 个？ |

判定规则：
- 好：依据具体到方案中的接口数/页面数/数据模型数
- 中：依据能指向方案中的模块但不够具体
- 差：依据不可验证（"中等""常规""经验"等），此人天数字本质上是拍的

依据质量为"差"的项 → 标注为"需补充依据"
```

### B. 漏项扫描

```
对照方案文档逐个模块扫描：

□ 方案中的每个模块 → 报价有人天吗？
□ 方案中的每个第三方依赖 → 报价有对应费用吗？
□ 方案中的每个里程碑 → 报价付款节点有对应吗？

常见漏项（对照检查）：
□ 环境搭建/CI/CD（方案有部署设计 → 报价有部署人天和服务费吗？）
□ 数据迁移（方案提到了旧数据 → 报价有迁移人天吗？）
□ 培训/文档（方案写了交付文档 → 报价有文档人天吗？）
□ 项目管理/沟通（报价有管理系数吗？）
□ 上线支持（方案写了部署 → 报价有上线支持人天吗？）
□ 差旅/驻场（方案或需求有提到吗？报价覆盖了吗？）
□ 第三方服务的增值税/汇率（如果是海外服务）

漏项 = 必须补，不是可选。
```

### C. 估算合理性交叉验证

```
1. 模块间类比：
   同一项目中相似复杂度的模块，人天是否相近？
   如果"用户模块"= 5 天而"订单模块"= 15 天，需要合理理由

2. 前后端比例：
   如果前端人天是后端的 3 倍 → 是不是隐含着复杂的前端需求方案没写清楚？
   如果后端人天是前端的 5 倍 → 是不是后端过度设计？

3. 人天 vs 时间线一致性：
   报价总计人天 ÷ 方案并行人数 ≈ 方案时间线吗？
   偏差 > 30% → 要么人天有问题，要么时间线有问题，要么并行度假设有问题

4. 异常值检测：
   单模块人天 > 总人天的 40% → 这个模块是不是该拆？
   某模块 0.5 天 → 0.5 天的工作量通常不存在。要么合并，要么说明
   某模块人天是整数（5、10、15）且依据质量"差" → 高度怀疑是拍的

5. 缓冲合理性：
   不确定性缓冲比例是否和方案中假设数量匹配？
   假设 5+ 但缓冲只有 10% → 缓冲不足
   假设 0-2 但缓冲 30% → 缓冲过度（除非项目本身高风险）
```

### D. 定价模型检查

```
□ 推荐模型是否匹配项目特征？
  - 范围明确、假设 ≤ 3 → 固定总价 OK
  - 范围模糊、多方面可能有变 → 固定总价 = 风险
  - 涉及新技术、无类似项目参考 → 人天更安全

□ 如果固定总价：
  - 是否有变更机制？（什么算变更？按人天还是二次报价？）
  - 范围基线是否明确？（"基于方案 v1 的需求范围"）
  - 不包含项是否列全？（没列全 = 变更和新增功能分不清）

□ 如果人天结算：
  - 单价是否合理？
  - 是否有上限保护？

□ 付款节点：
  - 尾款 ≥ 10%？
  - 里程碑触发条件 = 方案验收标准？（必须一致）
```

### E. 报价假设攻击

报价中的假设比方案中的假设更危险——因为报价假设直接关联到钱。

通过 Skill 工具加载 `found-assumption-attack`（Skill(skill: "found-assumption-attack")），对报价方案进行完整的假设攻击流程：

1. 提取报价中已声明的所有假设
2. 逐条攻击：成立概率、不成立后果（量化为对报价金额的影响）、退路、验证成本
3. 挖掘隐藏假设：报价未声明但实际依赖的前提

重点关注报价特有的隐藏假设场景：
□ "客户提供的信息准确完整" → 如果信息有误？
□ "客户方资源按时到位" → 如果延迟 1 个月？
□ "第三方服务按报价时的价格" → 如果明年涨价 30%？
□ "需求在报价后无重大变化" → 什么是"重大"？
□ "客户验收流程顺畅" → 如果验收反复 3 轮？
□ "开发期间无重大技术障碍" → 如果关键技术选型不 work？

输出时额外标注：每条假设不成立时对报价金额的量化影响。

## 评审结论

```
通过：
  条件：所有估价有可验证依据 + 无漏项 + 交叉验证合理 + 定价模型匹配 + 假设 ≤ 5 且都有标注
  结论：报价可锁定，进入展示材料阶段

需调整：
  条件（满足任一）：
  - 有估价依据为"差"的项
  - 有漏项
  - 人天和时间线不一致（偏差 > 30%）
  - 缓冲比例和假设数不匹配
  - 定价模型和项目特征不匹配
  结论：列出调整项，标注重审需要（> 3 项调整 → 必须重审）

阻塞：
  条件（满足任一）：
  - 报价漏掉了整个模块或关键依赖
  - 报价总人天明显不可能完成方案中的范围（如方案 8 个模块报价只有 10 人天）
  - 定价模型在当前约束下确定会赔钱
  - 关键假设几乎确定不成立
  结论：不建议继续，报价需重新制作
```

## 评审纪律

- **不压价也不抬价**：你的职责是检查逻辑一致性，不是替客户砍价或替公司抬价
- **怀疑每个整数**：5、10、15 天——整数往往不是算出来的
- **缺依据 ≠ 错**：没有依据的不一定估错了，但必须标注让报价者补
- **不开启哲学讨论**：不讨论"这个技术到底值多少钱"，只检查"这个数字和方案是否逻辑一致"

```markdown

### A. 依据质量
| 模块/角色 | 人天 | 依据 | 质量 | 问题 |
|-----------|------|------|------|------|

### B. 漏项
{逐项列出，对应方案出处}

### C. 交叉验证
{模块类比 / 前后端比 / 人天-时间线一致性 / 异常值 / 缓冲}

### D. 定价模型
{模型匹配度 / 变更机制 / 付款节点检查}

{通过 / 需调整 / 阻塞}
{具体项}
```

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| "人天估算本来就是经验活，没什么好审的" | 经验估算 = 有偏差的估算。审的就是偏差 |
| "总价看起来合理就行" | 总价合理 = 各项偏移恰好抵消。漏项不会自己填上 |
| "第三方费用按市场价写的，不用查" | 市场价在变。你写的是哪个月的市场价 |
| "管理成本不用单独列，压在开发人天里了" | 藏起来的管理成本 = 砍预算时第一个被砍 = 项目没 PM |
| "这些漏项后面发现了再补" | 报价漏了 = 客户不会补。后面都是你自己吃 |
