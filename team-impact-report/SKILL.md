# 异常与影响上报

## 两个方向

**方向 A — 看到异常但觉得「跟我无关」：**
```
1. 记录：哪个测试？错误输出？
2. 判断：之前是否通过？
3. 报告：详情 + 你的判断
4. 等待：开发者决定跳过还是修复
```

**方向 B — 明知会断但觉得「下次再说」：**
```
1. 记录：哪些模块受影响？具体需要改什么？
2. 标注：在 PR 描述或对话中明确标注
3. 报告：完整的连锁影响
4. 建议：修复顺序（A → B → C）
```

## 红线

```
❌ 「这个测试本来就不稳定」→ 报告
❌ 「这不是我改的」→ 报告
❌ 「下次再补」→ 现在记
❌ 「别人会统一改的」→ 标注谁需要改

Agent 没有权力替开发者过滤信息。
宁可报十个假阳性，不能漏一个真问题。
```

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| 「这个跟我改的无关」 | 有关无关由开发者判断，不是 agent |
| 「这个本来就有问题」 | 报告，让开发者确认 |
| 「大家都没发现，应该没事」 | 从众 ≠ 没问题 |
| 「先不管了继续」 | 报告完再继续 |
| 「看起来不影响主流程」 | 你说了不算，报告 |

> 事前评估影响范围请调用 impact-assessment（component）。
> 本 skill 只负责事后上报。
