# 增量编码

## 核心原则

**一次只做一个任务。完成后验证，然后才能进入下一个。**

编码不是自由创作，是按设计书和任务清单精准执行。

## The Gate Function

```
BEFORE starting any task:
→ 链式验证：这个任务的完成标准和验证方式定义了吗？
  → 没有 → 「任务分解未完成，请先补充完成标准和验证方式」

FOR each task in the list, from P-01 to P-N:

1. IMPLEMENT: 完成这个任务需要的代码改动
2. VERIFY: 对照任务的完成标准——满足了吗？
3. DESIGN SYNC: 改了什么 → 更新设计书（调用 design-sync）
4. MARK: ✅ P-{N} 完成
5. NEXT: 进入下一个任务

NEVER:
- 同时改多个任务
- 未经验证就标记完成
- 跳过某个任务
- 擅自增加不在任务列表中的改动
```

## 折返协议

执行中可能发现计划有问题，此时需要折返：

```
发现 plan 有问题（依赖遗漏/方案不对/任务顺序错）：
→ STOP 当前执行
→ 记录：为什么折返、影响了哪些任务
→ 回到计划阶段：更新 task-breakdown 或调整 plan
→ 报告开发者：折返原因 + 调整方案
→ 重新执行

发现设计书与代码不一致：
→ 先同步设计书（调用 design-sync）
→ 再继续执行

折返不是失败，是修正方向。
但每次折返都要记录原因，避免反复走回头路。
```

## 子 Agent 调度

如果任务列表中的多个任务满足以下所有条件，可拆分子 agent 并行执行：

```
□ 任务之间没有强耦合（A 的结果不依赖 B 的中间状态）
□ 每个任务都有明确的完成标准和验证方式
□ 不会修改同一个文件
□ 并发数不超过限制（单人 2，团队 4）
```

如果需要拆多个子 agent 并行执行：报告主 agent，由主 agent 读取 `comp-subagent-dispatch` 中的调度规则。子 agent 不应自己决定拆子 agent。

> 如果当前文件超过 300 行或一个类/函数有多种职责，建议调用 found-artifact-split 拆分。

## 语言选择指南

从 `.tws/project-map.md` 技术栈字段判断语言，加载对应组件 skill。

如果是后端逻辑编码：

```
调用对应语言的组件 skill：
- Python → backend-impl-python
- Java → backend-impl-java
- API 设计 → backend-api-design
- 数据库 → backend-db-design
```

如果是前端编码：

```
- UI 设计 → frontend-ui-design
- 前端逻辑 → frontend-impl
```

## 常见失败模式

| 表现 | 根本问题 |
|------|---------|
| 改一个地方顺手改了另一处 | 擅自增加了任务范围 |
| 「顺便重构了一下」 | 任务外的改动要另开任务 |
| 改完了没有自测 | 跳过验证环节 |
| 改 P-01 的时候动了 P-02 的内容 | 没有边界控制 |

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| 「这个改动跟任务相关，顺手改了」 | 顺手改 = 没有计划。要么另开任务，要么别改 |
| 「先不管验证，先把所有任务做完」 | 不做验证 = 不知道做对了没有 |
| 「这个很简单，不用测」 | 越简单越要测。说不用测的时候最需要测 |
| 「代码跟设计书差不多」 | 差不多 = 不一样。精准同步 |
| 「同时改两个任务效率更高」 | 同时改 = 同时错。出问题了不知道是哪个引起的 |

## 为什么重要

- 一次多做 ≠ 效率高。出问题反而更难定位
- 增量编码保证每步可回退 → 出错了只影响最近的改动
- 设计书同步保证做完一个任务就有一个任务的交付物
