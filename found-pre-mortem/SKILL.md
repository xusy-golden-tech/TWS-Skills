# Pre-Mortem

## 是什么

Pre-Mortem 是一种逆向风险识别方法：**假设项目/方案/计划在实施后已被认定为失败，然后反向推导最可能导致失败的原因。**

正常的风险分析是「未来可能发生什么？」——人的大脑不擅长这个。Pre-Mortem 是「它已经失败了，为什么？」——大脑擅长给已经发生的事找原因。

这就是它的力量：绕过乐观偏差，用你已经知道但下意识忽略的信息来发现真正的风险。

## 何时用

任何涉及实施计划、方案设计、架构决策的场景都可以触发：

- 方案评审 → 假设方案已实施，被客户认定失败
- 报价评审 → 假设报价已锁定，项目亏了
- 架构设计 → 假设架构已落地，扛不住实际流量
- 迁移计划 → 假设迁移已执行，数据丢了
- 重构计划 → 假设重构完成，系统比之前更差
- 任何「我觉得这个计划不错」的时刻 → 值得做一次

不适用于：需求澄清阶段（还没有方案/计划可审）、纯信息查询。

## 如何执行

### 第 1 步：设定场景

明确时间点和失败定义：

```
假设 {时间点，如 6 个月后}，{方案/计划/设计} 已经实施完成，
但被 {谁，如客户/用户/团队} 认定为失败。

失败标准：{什么算失败？如：超预算 50%、核心功能不可用、客户拒绝验收}

现在问自己：最可能导致这个结果的 3 个原因是什么？
```

关键：「失败标准」必须具体。模糊的「项目失败了」得不到有用的答案。

### 第 2 步：独立推导前 3 原因

**不要看被审文档自列的风险清单。** 先用自己的判断独立推导：

```
1. {最可能的原因一}
   - 为什么这是最可能的？
   - 这个原因在当前方案/计划中有被考虑到吗？
   - 如果有，缓解措施够吗？
   - 如果没有 → 这是最重要的发现

2. {第二可能的原因}
   ...

3. {第三可能的原因}
   ...
```

推导时问自己：
- 过去类似项目最大的坑是什么？
- 这个方案最脆弱的一环在哪？（最复杂？最依赖外部？最模糊？）
- 如果只能改一件事来拯救这个方案，改什么？

### 第 3 步：对照被审文档的风险清单

```
被审文档列了 X 个风险，覆盖了以上 3 个中的 Y 个：
- 已覆盖：{哪些} → 缓解措施是否可操作？
- 未覆盖：{哪些} → 这是评审中最重要的发现。最致命的失败原因没有出现在文档自己的风险认知里
```

### 第 4 步：检查缓解措施

对文档中已列的风险，检查：

```
□ 缓解措施是否具体可执行？（「加强沟通」不是缓解措施）
□ 是否有残留风险？（缓解后仍存在、未解决的风险）
□ 残留风险是否被标注？
```

## 输出格式

```markdown
## Pre-Mortem

### 场景
{时间点 + 失败定义}

### 前 3 失败原因
1. {原因} — {为什么 / 方案有没有考虑到}
2. {原因}
3. {原因}

### 对照文档风险清单
- 文档列了 X 个风险
- 覆盖了 3 个中的 Y 个
- 遗漏：{未覆盖的原因}
- 缓解措施评估：{具体可操作？有残留风险？}

### 最重要的发现
{一句话：如果不改这个，项目大概率失败}
```

## 原则

- **先不看文档自列的风险**：看了就会被锚定。先想自己的，再对照
- **前 3，不是前 10**：精力有限，排优先级。前 3 以外的不提
- **不给假的原因**：如果确实只能想到 2 个有说服力的，就写 2 个。编一个假的比少一个更糟
- **原因必须具体**：「沟通问题」不是原因，「客户方对接人每 2 周才回复一次需求确认」才是

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| 「这个方案挺简单的，不需要 Pre-Mortem」 | 越简单越容易觉得没问题 = 越容易漏 |
| 「文档已经列了风险清单，不用再做了」 | Pre-Mortem 的价值就在「不看文档自己先想」。看了再想 = 被锚定了 |
| 「我只想到 1 个原因，算了不做了」 | 1 个原因也是发现。但如果真的只有 1 个，再想想——是不是忽略了什么 |
| 「这个原因不太可能发生」 | Pre-Mortem 的前提是「它已经发生了」。在已发生的世界里，没有不太可能 |
