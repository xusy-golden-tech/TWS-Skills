# 部署

## 核心原则

**能回滚的部署才是安全的部署。**

一次部署是否成功，不是以「上线了」为标准，是以「上线后验证通过且可回滚」为标准。

## The Gate Function

```
BEFORE deploying:
1. 环境检查
   - 依赖全部安装？（pip install / npm ci / mvn dependency:resolve）
   - 配置文件齐全？（.env / config.* 存在）
   - 数据库可连接？

2. 构建确认
   - 编译/打包通过
   - 产物检查（文件存在、大小合理）
   - 记录构建时间和版本号

3. 数据库迁移
   - 有变更 → 先跑 migration 预览（dry-run）
   - 验证可回退 → 确认有对应的 rollback 脚本
   - 不可逆操作（DROP COLUMN 等）→ 先在测试环境验证

4. 上线
   - 切换到新版本
   - 先灰度（如有条件）

5. 验证
   - 核心功能正常（健康检查端点返回 200）
   - 日志无异常（ERROR 级别日志不增加）
   - 告警规则正常（没有误报）

6. 回滚方案
   - 出问题了怎么回退？（回滚到上一个版本）
   - 回滚脚本就绪了吗？
   - 回滚后需要做数据恢复吗？

AFTER deploying:
- 记录部署时间、版本号、变更内容
- 通知相关人员
```

## 常见失败模式

| 表现 | 原因 | 预防 |
|------|------|------|
| 部署后页面白屏 | 前端构建产物有问题 | 上线前验证构建产物 |
| 数据库迁移卡住 | 没跑 dry-run | 先 dry-run 再执行 |
| 环境变量缺失 | .env 没配全 | 上线前 checklist 确认 |
| 新版本启动失败 | 依赖版本不兼容 | 验证依赖安装结果 |

## 部署后检查清单

```
□ 健康检查端点正常
□ 核心业务流程走得通
□ 日志无新增错误
□ 资源使用（CPU/内存）无明显增长
□ 版本号正确
```

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| 「先上了再说，不行再回滚」 | 没有回滚方案就上 = 赌 |
| 「就改了一行配置，不用部署流程」 | 改配置最容易出问题，走完整流程 |
| 「测试环境测过了，生产一样」 | 生产环境配置不同，不能等同 |
