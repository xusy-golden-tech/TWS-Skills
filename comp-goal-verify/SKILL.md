# 目标回溯验证

## 核心原则

**测试通过 ≠ 功能可用。**

comp-test 验证的是「测试跑过了」。
本 skill 验证的是「设计书描述的功能在代码中真实存在并且连接正确」。

## 对抗姿态

你是审查者，不是执行者的朋友。你的工作假设：

```
假设：设计书描述的功能没有真正实现。
目标：用代码证据推翻这个假设。
推翻不了 → 报告问题。
```

禁止软化：
- ❌ "测试都过了，应该没问题"
- ❌ "代码看着差不多"
- ❌ "文件存在，基本就实现了"
- ❌ "这个改动很小，不用仔细查"

## The Gate Function

```
AFTER comp-test passes, BEFORE marking task done:

1. LOAD: 设计书「验收标准」节（如果设计书有结构化验收标准，直接用；否则从「涉及模块」「接口变更」提炼）
2. VERIFY: 对每个功能目标执行四层检查
3. REPORT: 输出验证报告
4. ONLY THEN: 通过 → 标记完成；阻塞 → 上报主 agent
```

## Step 0: 图中验证接线

L3 接线性检查必须用代码图验证，不能仅靠 Grep 搜索字符串。

**必须操作：** 通过 Skill 工具加载 `found-tws-graph-usage`（Skill(skill: "found-tws-graph-usage")），按其中指引完成前置检查和以下查询：

```
1. tws-graph --version              ← 检查可用性（不可用则 pip install -e tws-graph/）

2. tws-graph calls <新增API路由> --inbound  ← 验证前端是否调用了新路由

3. tws-graph trace <前端组件> <后端路由>     ← 验证端到端接线路径完整

4. tws-graph calls <新增模块>                ← 验证新增模块的导入和调用关系
```

错误处理详见 `found-tws-graph-usage`。图返回空时标注 provenance=heuristic，退回到 Grep + Read 手动追踪。

## 验证流程

### 第一步：提取目标

从设计书提取验证目标：

```
如果设计书有「验收标准」节 → 直接使用
否则 → 从「涉及模块」和「接口变更」两节提炼

提取内容：
1. 功能目标：这个改动要实现什么？
2. 涉及的组件：哪些文件/模块应该被创建或修改？
3. 接线关系：组件之间应该怎么连接？
```

### 第二步：四层验证

对每个功能目标，执行四层检查：

```
L1 — 存在性：文件存在吗？
  → 用 Glob 或 Bash 检查文件是否存在
  → 文件不存在 → BLOCKER
  → 文件存在 → 继续

L2 — 实质性：内容是真实实现还是占位符？
  用 Grep 检查桩代码模式：
  - TODO / FIXME / XXX / HACK / PLACEHOLDER
  - return None / return {} / return []
  - pass / ... / NotImplemented
  - "Not implemented" / "coming soon" / "暂未实现"
  - 空函数体（只有 return 或 pass）
  - 只有 console.log / print 的函数
  → 存在桩模式 → BLOCKER
  → 内容实质 → 继续

L3 — 接线性：组件之间实际连接了吗？
  根据设计书的接线关系检查：
  - 前端调了后端 API？→ grep fetch/axios 调用
  - API 连了数据库/服务？→ grep 数据库查询/服务调用
  - 事件/回调被正确绑定？→ grep 事件绑定
  - 路由指向了正确的处理器？→ grep 路由定义
  - 新增模块被正确导入？→ grep import/require
  → 接线缺失 → BLOCKER
  → 接线存在 → 继续

L4 — 一致性：实现与设计书描述一致吗？
  - 接口签名匹配？（参数名、类型、返回值）
  - 行为描述匹配？（设计书说返回 X，代码真的返回 X？）
  - 错误处理匹配？（设计书说返回 401，代码真的返回 401？）
  → 不一致 → WARNING（可能是合理偏差，需人工确认）
```

### 第三步：输出报告

```markdown
## 目标回溯验证报告

### 功能：{功能名}

| 检查层 | 对象 | 结果 | 证据 |
|--------|------|------|------|
| L1 存在性 | {文件路径} | ✅/❌ | {一句话} |
| L2 实质性 | {函数/模块} | ✅/❌ | {一句话} |
| L3 接线性 | {A→B} | ✅/❌ | {一句话} |
| L4 一致性 | {接口/行为} | ✅/⚠️ | {一句话} |

### 结论
- BLOCKER 数：{N}（必须修复才能标记完成）
- WARNING 数：{N}（需人工确认，不阻塞）
- 总体：✅ 通过 / ❌ 阻塞 / ⚠️ 需人工确认
```

## 执行方式

本 skill 由**独立的审查子 agent** 执行：

```
主 agent 派审查子 agent 时：
- 提供：设计书路径 + 改动文件列表
- 审查子 agent 不读执行者的对话历史
- 审查子 agent 用 isolated 上下文启动
- 审查结果返回主 agent 决策
```

## 与 comp-test 的关系

```
comp-test（测试子 agent）：
  → 跑测试，确认测试通过
  → 检查边界条件
  → 回归验证

comp-goal-verify（审查子 agent）：
  → 在 comp-test 通过后执行
  → 不跑测试，而是检查代码本身
  → 确认代码真实实现了设计书描述的功能

两者互补，不替代。
```

## 何时使用

```
简化路径（≤2 文件，单模块，无接口变更）：
  → 跳过

完整路径，满足以下任一条件时必须执行：
  □ 改动涉及 3+ 个文件
  □ 改动涉及接口变更（API 路由、事件、公共函数签名）
  □ 改动涉及安全相关功能（认证、鉴权、数据处理）
  □ 设计书验收标准中有「接线验证」项

中等风险任务：
  → 主 agent 判断是否执行
```

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| 「测试都过了，不用再验证了」 | 测试通过是 comp-test 的事。本 skill 检查的是测试没覆盖的：桩代码、未接线、不一致 |
| 「这个改动很小，跳过吧」 | 越小的改动越容易出桩代码，因为"反正很快" |
| 「我看过代码了，没问题」 | 你是执行者，你的判断被自己的实现思路污染了。独立审查才能发现问题 |
| 「文件存在就是实现了」 | 存在 ≠ 实现。一个只有 `return None` 的函数也存在 |
