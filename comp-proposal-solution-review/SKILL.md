# 方案评审

## 核心原则

**假设方案有问题，直到证据推翻这个假设。**

你不是来找茬的。但如果不带着怀疑审视方案，这个方案的漏洞会在报价阶段变成真金白银的代价。

**为什么需要独立评审：** 方案设计者和方案评审者是不同的人（不同子 agent，干净上下文）。设计者对自己的方案有盲区——他花了几小时设计的东西，潜意识里会捍卫每一个选择。评审者的价值就是不带感情地攻击它。

## 前置输入

- 需求摘要（`comp-proposal-discovery` 的输出）
- 方案文档（`comp-proposal-solution` 的输出）

两个都要完整读取。方案脱离需求审 = 不知道方案是否回应了需求。需求脱离方案审 = 不知道设计的合理性。

## 子能力

### A. 需求覆盖检查

逐条对照需求摘要中的每条需求，检查方案是否有回应：

```
| # | 需求 | 方案对应内容 | 覆盖 | 备注 |
|---|------|------------|------|------|
| 1 | 用户注册登录 | 模块"用户中心" | 完整 | |
| 2 | 报表导出 Excel | 未找到 | 缺失 | 需求 R7 要求导出，方案未提及 |
| 3 | "系统要快" | 未找到量化定义 | 部分 | 需求中的非功能需求"快"未在方案中量化 |

判定规则：
- 完整：方案明确了怎么做
- 部分：方案提到了但不够具体（如"我们会做报表"但没说什么报表什么格式）
- 缺失：方案中找不到对应的设计
- 过度：方案做了需求以外的事（标注出来，可能是 scope creep）
```

**为什么逐条对照：** 这是整个评审的地基。需求没覆盖完 = 后面架构/模块/风险分析都是基于不完整的信息。

### B. 架构合理性检查

```
逐项检查：

1. 架构风格是否匹配项目规模？
   - 2 周的 CRUD 项目用了微服务？→ 过度设计
   - 多团队多子系统用了一个单体？→ 可能设计不足
   - 标注：不匹配项 + 建议

2. 模块边界是否清晰？
   - 有没有两个模块职责重叠？（如 "用户模块" 和 "权限模块" 都管角色分配）
   - 有没有模块职责太宽？（如 "业务模块" 包了所有业务逻辑）
   - 标注：边界模糊项 + 建议拆分或合并

3. 依赖关系是否有问题？
   - 循环依赖：A 依赖 B，B 也依赖 A → 设计有问题
   - 不合理依赖：底层模块依赖上层模块 → 倒置
   - 标注：问题依赖 + 建议方向

4. 技术选型理由是否可辩护？
   - "因为流行" → 不是理由，是偷懒
   - "因为团队熟悉" → 如果客户维护团队不熟悉呢？——因为这是乙方场景，维护可能是客户自己做
   - "因为在某某大厂也用" → 不是理由，大厂的场景和你不一样
   - 标注：不可辩护的选型 + 追问
```

### C. 范围适当性检查

```
检查方案有没有越界或不足：

1. Scope Creep（范围蔓延）：
   - 方案中的交付物是否超出了需求摘要的"本次做"范围？
   - 如果有：是合理的扩展还是不必要的工作？谁为此买单？

2. 范围不足：
   - 需求摘要"本次做"范围内的内容，方案有没有遗漏？
   - 特别是"潜在需求"中被标注为"建议做"的部分

3. 交付节奏是否现实：
   - 并行标注是否合理？（标注可并行的模块是否真的无依赖？）
   - 关键路径计算：从第一个里程碑到最后一个，依赖关系是否支持这个时间线？
   - 如果时间 × 并行人数 > 可用时间 × 1.3 → 时间线不可行
```

### D. 风险独立扫描

不看方案文档自列的风险——先自己做 Pre-Mortem，再和方案的风险清单对比。

执行 Pre-Mortem 方法论：通过 Skill 工具加载 `found-pre-mortem`（Skill(skill: "found-pre-mortem")），设定场景为「假设 6 个月后，这个方案实施完成，但项目被客户认定为失败」。

Pre-Mortem 完成后，对照方案文档的风险清单：
- 方案列了 X 个风险，覆盖了 Pre-Mortem 前 3 原因中的 Y 个
- 如果最致命的失败原因没出现在方案风险清单中 → 这是最重要的发现

额外检查：
- 方案对每个风险的缓解措施是否实际可操作？（"加强沟通"不是缓解措施）
- 方案是否标注了残留风险？（缓解后仍存在的风险）

### E. 假设攻击

对方案中的假设执行系统化攻击。通过 Skill 工具加载 `found-assumption-attack`（Skill(skill: "found-assumption-attack")），对方案文档进行完整的假设攻击流程：

1. 提取方案中已声明的所有假设
2. 逐条攻击：成立概率、不成立后果、退路、验证成本
3. 挖掘隐藏假设：方案未声明但实际依赖的前提
4. 输出假设健康度评估

重点关注以下方案特有的隐藏假设场景：
- "客户会按时提供所需资料" → 如果延迟 2 周呢？
- "需求不会发生重大变化" → 如果核心需求变了呢？
- "第三方服务按文档描述的运行" → 如果实际行为不一致呢？
- "客户方对接人有技术决策权" → 如果每次都要层层审批呢？
- "客户方提供的硬件/网络环境满足要求" → 如果不满足呢？

## 评审结论

三个等级的判断标准：

```
通过：
  条件：需求全覆盖 + 架构合理 + 范围适度 + 风险已识别且缓解有效 + 假设 ≤ 5 个且都有退路
  结论：方案可以锁定，进入报价阶段

需修改：
  条件（满足任一）：
  - 有 1+ 需求未覆盖或部分覆盖
  - 架构有不合理但可修复的设计（非致命）
  - 有 scope creep 或范围遗漏
  - 有技术选型理由不可辩护
  结论：列出修改项，标注是否需要重新评审
  重要：如果修改项超过 3 个，必须重新评审

阻塞：
  条件（满足任一）：
  - 核心需求完全未覆盖（方案方向就错了）
  - 架构有致命缺陷（选型根本无法满足约束）
  - 交付节奏在数学上不可能
  - 关键假设几乎确定不成立
  - 方案范围与需求范围严重错位（做的东西和客户要的不是一个）
  结论：不建议进入报价阶段，必须重新设计方案
```

## 评审纪律

- **不看面子**：方案写得详细不代表正确。不能因为文档长就给通过
- **不说空话**：每条意见必须有具体指向 + 可行建议。"架构不合理"等于没说
- **不替设计者改**：指出问题给出方向，具体怎么改是设计者的事
- **不翻需求旧账**：如果需求本身有问题，标注"需求层面建议确认"，但不要因为需求问题阻塞方案评审。方案是在给定需求下的最优解，不是你判断需求好坏的地方

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| "方案写得挺详细的，应该没问题" | 详细 ≠ 正确。字数不替代逻辑 |
| "这个风险不太可能发生" | 你觉得不太可能 = 不会做缓解 = 一旦发生了就是灾难 |
| "时间紧，先过了吧" | 评审省的时间 = 后面返工的时间 × 10 |
| "这个建议太细节了，不影响大局" | 评审不提 = 没人会提 = 带着问题进报价 |
| "修改项太多了，要不我自己改了得了" | 你不是来重写方案的。评审 = 找问题，设计者 = 解决问题 |
