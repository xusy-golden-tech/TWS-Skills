# 代码审查

## 核心原则

**审查者和执行者必须是不同的人。上下文必须是干净的。**

> 审查方法论详见 found-review-methodology。
> 任何审查必须新开子 agent，只提供必要事实，不包含引导性内容。
> 派审查子 agent 时，遵循「防止上下文污染」规则——声明不读记忆文件，使用 `context:"isolated"` 启动子 agent。

## 与 review-methodology 的边界

`found-review-methodology` 只规定“如何派一个干净、独立的审查者”；`comp-code-review` 规定“审查者拿到任务后具体查什么、怎么报告”。不要把代码审查清单复制到 `found-review-methodology`，也不要把派发隔离规则复制到各个审查清单中。

**审查的是逻辑和设计，不是风格和格式——但规约例外。**

规约是团队约定，不遵守规约 = 跟团队不一致。

## 审查清单

审查代码时：

### 代码审查（7 个维度逐一检查）

#### D1：逻辑正确性
- 每个条件分支都有对应的处理吗？
- 空值 / None / undefined 处理了吗？
- 错误路径能走到正确的错误处理吗？
- 循环有终止条件吗？

#### D2：测试覆盖
- 新增代码的所有公共接口有测试吗？
- 正常路径 + 边界条件 + 错误路径都覆盖了？
- 测试断言检查了正确的内容？（不是 assert True）

#### D3：设计书同步
- 代码实现的接口签名与设计书一致吗？
- 新增的行为在设计书中有描述吗？
- 删除/修改的行为在设计书中有记录吗？

#### D4：规约遵守
- 编码规约（路径见 .tws/project-map.md）逐条核对了吗？
- 命名、缩进、注释规范、错误处理方式是否一致？

#### D5：安全性
- 外部输入有验证吗？（用户输入、API 参数、文件内容）
- 有注入风险吗？（SQL、命令注入、XSS）
- 权限检查到位吗？

#### D6：接线完整性
- 新增的函数/方法被正确调用了吗？
- 新增的 API 路由在前端/调用方有对应调用吗？
- 新增的事件/回调被正确订阅了吗？

#### D7：架构健康度
- 修复是否引入了对其他模块的不必要依赖（新耦合）？
- 是否在已有 hack/workaround 上继续叠加逻辑？如果是，有没有更干净的做法？
- 修复逻辑放在了正确的位置（正确的模块/层级）吗？还是散落在不该放的地方？
- 修复后这段代码的可维护性是变好了还是变差了？将来需求变了容易改吗？
- 有没有破坏既有的抽象层次或设计模式？

审查设计书时：

```
□ 结构符合设计书规约吗？（路径见 .tws/project-map.md → design-conventions）
□ 所有必需章节都写了？
□ 接口定义清晰吗？
□ 与其他设计书一致吗？
```

## 优先级

```
正确性 > 安全性 > 规约遵守 > 性能 > 风格
```

## 报告格式

```markdown
## 代码审查报告

### 审查对象
{文件列表}

### 发现

| # | 维度 | 严重性 | 描述 | 位置 |
|---|------|--------|------|------|
| 1 | D1 | A/B | {问题} | {文件:行号} |

### 结论
- A 类问题：{N} 个（必须修）
- B 类问题：{N} 个（建议修）
- 总体：通过 / 有条件通过 / 阻塞
```

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| 「执行者已经自查过了」 | 审查必须独立，不能复用执行者视角 |
| 「只看 diff 就够了」 | diff 需要结合设计书、调用方和测试一起判断 |
| 「没有明显 bug 就通过」 | 审查还要看同步、接线、安全和架构健康度 |
