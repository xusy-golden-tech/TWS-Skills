# 假设攻击

## 是什么

假设攻击是一种系统化检验方法：**逐条找出一个方案/计划/报价中依赖的假设（包括写出来的和没写出来的），然后攻击每一条——它成立的概率有多高？不成立的话后果是什么？有没有退路？**

项目出问题很少是因为「已知的风险发生了」，更多是因为「某个假设不成立，而没有人意识到这个假设存在」。

## 何时用

任何依赖假设的产物都可以触发：

- 方案设计 → 方案中声明的技术/资源/环境假设
- 报价方案 → 报价中的人和天/费用估算所依赖的假设
- 架构设计 → 架构选型依赖的性能/扩展性假设
- 迁移计划 → 迁移依赖的兼容性/数据完整性假设
- 项目计划 → 排期依赖的资源/依赖可用性假设

不适用于：需求澄清阶段（此时假设还没形成）、纯事实陈述（没有假设可攻击）。

## 核心原则

**每个决策背后都有一个可以被质疑的假设。你的任务就是找出来，质疑它。**

设计者/报价者写出来的假设是冰山露出来的部分。水下才是危险所在。

## 如何执行

### 第 1 步：提取已声明的假设

从被审文档中逐条提取写出来的假设：

```
| # | 假设内容 | 出处 |
|---|---------|------|
| 1 | "客户方会按时提供所需资料" | 方案风险清单第 3 条 |
| 2 | "第三方 API 按文档描述的运行" | 方案技术选型说明 |
| ... | ... | ... |
```

### 第 2 步：攻击每条已声明的假设

对每条已声明的假设，回答四个问题：

```
| 假设 | 成立概率 | 判断依据 | 不成立的后果 | 退路 | 验证成本 |
|------|---------|---------|------------|------|---------|
| "客户会按时提供资料" | 中 | 客户方历史上资料提供延迟 1-3 周 | 项目前 2 周无法启动，人天浪费 | 方案未提供退路 | 低成本：开工前 1 周直接问客户要资料清单，测试响应速度 |
```

四个问题的含义：

- **成立概率（高/中/低）**：不是感觉，是依据。有历史数据用历史数据，没有就说明「无数据，判断依据为经验」
- **不成立的后果**：量化的影响。「项目延期」不如「关键路径延长 2 周，涉及 3 人空转」
- **退路**：假设不成立时有替代方案吗？文档写了吗？没写 = 没有退路
- **验证成本**：有没有低成本方式在早期验证这个假设？低成本 = 应该在动手前验证

### 第 3 步：挖掘隐藏假设

这是最关键的一步。隐藏假设 = 文档没有写出来但实际上依赖的前提。

常见隐藏假设分类：

**资源类：**
- 客户方资源（人员/硬件/网络/许可证）按时到位
- 第三方服务按预期可用且不涨价
- 团队不会有人离职或请长假

**需求类：**
- 需求在实施期间不会发生重大变化
- 客户方对接人有技术决策权，无需层层审批
- 已确认的需求各方理解一致，不会事后翻盘

**执行类：**
- 关键技术选型在开发期间保持稳定（不出现 bug、不弃用）
- 开发期间无重大技术障碍
- 所有依赖方（分包/第三方）按约定的标准交付

**验收类：**
- 客户验收流程顺畅（不会反复拉锯 3 轮以上）
- 验收标准已在需求阶段达成共识，不会追加
- 客户方运维能力足以接管交付后的系统

**报价特有：**
- 人天估算的基础在实施期间不变（一个人天对应的工作量不变）
- 报价时的第三方服务价格在项目周期内不变
- 范围基线清晰，变更和新增的边界无争议

```
挖掘方法：不是挨个检查上面的分类清单，而是问自己：
- 如果我是负责实施这个方案的人，我最怕什么「以为是这样但其实不是」的事？
- 这个方案的哪个环节最依赖「别人按我们想的做」？
- 如果只准给一条建议让这个方案更稳，我会建议在动手前确认什么？
```

### 第 4 步：输出假设攻击结论

```
- 已声明假设 X 条：高概率 Y，中概率 Z，低概率 W
- 隐藏假设 M 条：高风险 N 条（不成立 → 方案/报价需要重大调整）
- 整体假设健康度：{健康 / 关注 / 危险}
  - 健康：假设 ≤ 5，全部高概率或有退路，无高风险隐藏假设
  - 关注：有 1-2 个低概率或无退路的假设，或 1-2 个高风险隐藏假设
  - 危险：关键假设几乎确定不成立，或有 3+ 高风险隐藏假设
```

## 输出格式

```markdown
## 假设攻击

### 已声明假设
| 假设 | 概率 | 依据 | 不成立后果 | 退路 | 验证建议 |
|------|------|------|----------|------|---------|

### 隐藏假设
| 假设 | 风险 | 不成立后果 | 建议 |
|------|------|----------|------|

### 结论
- 假设总数：X 已声明 + Y 隐藏 = Z
- 高风险项：N（列出）
- 假设健康度：{健康 / 关注 / 危险}
```

## 原则

- **概率不是感觉**：说「高」要有依据。没有依据就说「无数据」，但标注出来
- **挖掘隐藏假设是核心价值**：已声明的假设设计者自己知道，真正的发现在水下
- **不只攻击，还要验证路径**：每条高风险假设都要有验证建议——用什么低成本方式可以在动手前确认？
- **数量不是指标**：10 条低质量假设不如 3 条有洞察力的发现。不要为了凑数编假设

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| 「假设大家都懂的，没必要逐条审」 | 假设 = 你以为大家懂但每个人理解不一样 |
| 「这个假设太明显了，不可能不成立」 | 最明显的假设往往是最脆弱的——因为没人想过去验证 |
| 「隐藏假设没法穷举，意思一下就行」 | 不穷举 ≠ 不认真。前 3 个最危险的隐藏假设发现价值远大于 20 条不痛不痒的 |
| 「假设是方案设计者的事，评审不该替他想」 | 挖掘隐藏假设 = 评审的核心价值之一。设计者的盲区正是评审应该照亮的地方 |
