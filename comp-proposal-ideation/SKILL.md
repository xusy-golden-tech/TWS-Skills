# 方案构思

## 核心原则

**第一个想到的方案不一定是最好方案。**

看到需求后，人类和 AI 都会倾向于用第一个冒出来的思路直接开干。这一步强制停下来，问：这个问题还可以怎么解？每种解法赌的是什么假设？

## 前置输入

- 需求摘要（或其他流程的需求分析输出）
- 关键约束（时间/预算/技术栈/合规）

## 适用场景

本 skill 被以下 flow 调用：

| flow | 调用时机 |
|---|---|
| flow-build-solution | 需求澄清之后、方案设计之前 |
| flow-new-project | 需求分析之后、架构设计之前 |
| flow-add-feature | 需求分析之后、设计书之前 |
| flow-refactor | 现状分析之后、重构策略之前 |

也可单独调用——当你需要在动手之前穷尽可能性时。

## 子能力

### A. 发散探索

从至少 3 个不同视角，各自想出一种解法思路。不是 3 个"微妙变化"，是 3 个真正不同的方向：

```
视角 1 — 最省钱的解法（成本优先）
  思路：{一句话}
  核心设计：{关键设计决策}
  复杂度：{低/中/高} — 复杂度来源
  第三方依赖：{有/无，如果有是什么}
  风险：{最大的风险是什么}

视角 2 — 最稳的解法（风险优先）
  思路：{一句话}
  核心设计：{关键设计决策}
  复杂度：{低/中/高} — 复杂度来源
  第三方依赖：{有/无，如果有是什么}
  风险：{为什么稳}

视角 3 — 最灵活的解法（扩展性优先）
  思路：{一句话}
  核心设计：{关键设计决策}
  复杂度：{低/中/高} — 复杂度来源
  第三方依赖：{有/无，如果有是什么}
  风险：{最大的风险是什么}

视角 4（可选）— 最快交付的解法（时间优先）
  仅当有硬性交付期限时探索
```

每个视角必须够不同——如果视角 1 和视角 2 只是"用 Go 还是 Java"，那不够。真正不同的方向是架构风格、数据模型、甚至"要不要做这个"的差异。

### B. 假设映射

对每种解法思路，列出它成立必须依赖的假设：

```
| # | 假设 | 如果不成立会怎样 | 成立概率（高/中/低） |
|---|------|----------------|-------------------|
| 1 | 第三方 API 支持批量查询 | 性能下降 80%，方案不可行 | 中（文档说支持但未验证） |
| 2 | 客户能接受简化的权限模型 | 需求变更，需加完整 RBAC | 低（客户 RFP 明确写了细粒度权限） |
| 3 | ... | | |
```

规则：
- 每条假设必须具体，不能是"项目顺利"
- 成立概率的判断必须给依据——为什么你觉得是高/中/低
- 假设超过 5 条的方案 = 高度不确定，打分时要额外谨慎

### C. 比较与收敛

把所有思路摆在一起，从约束匹配度、假设数量、技术风险三个维度比较：

```
| 维度 | 视角 1（省钱） | 视角 2（稳） | 视角 3（灵活） | 视角 4（快） |
|------|-------------|------------|-------------|-----------|
| 匹配需求 | 完整/部分/缺失 | | | |
| 匹配约束 | 通过/有风险/违反 | | | |
| 假设数 | N | | | |
| 高风险假设 | N | | | |
| 复杂度 | 低/中/高 | | | |
| 可扩展性 | 低/中/高 | | | |
```

> **AI 编程下的方案选择原则：**
> 在 AI 辅助编程中，不要用人天估算来选择方案。"10 人天的方案"和"20 人天的方案"在实际 AI 编码中差异远小于表面数字——10+ 人天的东西往往一两个小时就能做完。人天数字反映的是传统人工开发的时间感，在 AI 编程下已失真。
> 方案选择应基于：约束匹配度、假设风险、技术复杂度、可维护性。人天估算是报价的事，不是选方案的事。

然后做收敛，从最不被约束支持的开始淘汰：

```
淘汰 1：{视角 X} — {淘汰理由，绑定约束或假设}
淘汰 2：{视角 Y} — {淘汰理由}
...

推荐：{视角 Z}
推荐理由：{为什么 Z 是最优选择，绑约束和风险}
```

### D. 决策输出

最终方案构思的输出不是长篇方案，是一份简洁的决策记录：

```markdown
## 方案构思

### 探索的思路
{列表：我们考虑了哪几种解法}

### 推荐方案
{视角 Z — 一句话}

### 为什么不是其他方案
- 方案 A（省钱）：淘汰 — {理由}
- 方案 B（稳）：  淘汰 — {理由}
- 方案 C（灵活）：淘汰 — {理由}

### 关键假设（需在后续验证）
- {假设 1} → 验证方式：{怎么低成本验证}
- {假设 2} → 验证方式：{同上}

### 推荐进入方案设计
{一句话结论}
```

## 复杂度门禁

如果明确满足以下全部条件，跳过方案构思直接进入方案设计：

```
□ 只有一种技术可行的解法（约束把其他路都堵死了）
□ 方案不涉及架构决策（纯 CRUD 无争议）
□ 项目周期 ≤ 1 周
```

## 常见失败模式

| 表现 | 根本问题 | 正确做法 |
|------|---------|---------|
| 3 个视角只是在同一架构下换技术栈 | 没真正发散 | 追问：如果不做这个系统呢？如果换个数据模型呢？ |
| 每个视角只写一句话 | 没深入想 | 每个视角至少要有核心设计 + 最大风险 |
| 假设全是"项目顺利"之类的 | 没做针对性思考 | 每个视角最脆弱的地方就是它赌的假设 |
| 淘汰理由 = "不太合适" | 没绑约束 | 淘汰理由必须绑定具体约束或假设 |

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| "这需求很简单，只有一种做法" | 只有一种做法 = 你没认真想。至少从成本/风险/灵活性三个角度各看一次 |
| "多想几种方案太花时间了" | 现在花 10 分钟想，比花 10 天返工便宜 |
| "方案设计里自然会考虑这些" | 方案设计是纵向深入，构思是横向发散。不在构思阶段发散，设计阶段就不会有真正的对比 |
| "方案 A 人天更少所以选 A" | 在 AI 编程下，人天差异没有意义。10 人天和 20 人天的方案 AI 做起来可能只差半小时。用复杂度、风险、假设数选方案，别用人天 |
| "淘汰的理由后面评审会发现的" | 评审发现"为什么没考虑 X" → 已经晚了。构思阶段自己先淘汰并记录，评审时才有底气 |
