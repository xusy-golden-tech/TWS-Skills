# 设计书撰写

## 核心原则

**没有设计书就不写代码。**

设计书不是文档任务，是编码任务的前置条件。跳过设计书 ≈ 蒙着眼睛写代码。

## The Gate Function

> 如果本设计书超过 200 行或覆盖 3 个以上模块，建议调用 found-artifact-split 拆分。

```
BEFORE writing any code:

1. 确定涉及的文件和模块
2. 描述实现方案
3. 定义所有接口变更（函数签名、API 路由、事件）
4. 标注测试要点
5. 输出设计书，等待用户确认
6. ONLY THEN: 进入任务分解（调用 task-breakdown）
```

## 输出格式

````markdown
## 设计书：[功能名]

### 涉及模块
- {模块A}：{改动描述}

### 实现方案
{简短描述，不做多方案对比}

### 接口变更（必填，无则写「无」）
- {接口名}：{变更内容}

### 验收标准（编码、测试子 agent 直接使用本节，不需要读全文）

#### 功能断言（必须全部通过）
- [ ] {具体断言，例如：POST /api/login 正确凭证返回 200}
- [ ] {具体断言}

#### 边界条件
- [ ] {边界断言}

#### 错误处理
- [ ] {错误场景断言}

#### 接线验证（如涉及多组件）
- [ ] {组件 A 调用了组件 B 的接口}
- [ ] {数据从 X 流到 Y}

### 规约遵守
- 检查编码规约文件（路径见 .tws/project-map.md）中的相关规则
- 本节改动的代码是否与规约一致？

### 决策记录
- {技术决策1}：{选择什么 + 为什么（按技术栈惯例 / 用户说了什么）}
- {技术决策2}：{同上}

> 无论是用户选的还是 agent 自己定的，都要记录。
> 下一个人看到设计书就知道「为什么这么做」。

### 变更履历
- {YYYY-MM-DD}：{初版创建 / 修改内容} — {原因}

> 每次修改设计书时，在履历表追加一行。
> 不要覆盖之前的履历。

## 禁止引导性记述

设计书和代码注释中不允许出现影响审查者判断的引导性语言：

```
❌ 「这个实现很简单」→ 暗示审查者不用仔细看
❌ 「这里应该没问题」→ 暗示审查者跳过
❌ 「标准实现，不用 review」→ 暗示审查者不用审
❌ 「后续优化」→ 暗示这个遗留问题不重要
❌ 「暂时这样」→ 暗示这不是最终方案，不用认真审

✅ 只写事实：「这个接口返回 {url, created_at} 两个字段」
✅ 只写理由：「选择 OSS 是因为用户文件平均 > 10MB」
✅ 遗留问题标注：「TODO：上传进度条未实现 — 下一迭代处理」
```

**原则：** 设计书的每一句都应该让审查者更警惕，而不是更放松。

### 连锁影响（如有）
- {会影响到什么模块/功能}
````

## 常见失败模式

| 表现 | 根本问题 | 正确做法 |
|------|---------|---------|
| 写得很笼统「优化一下」 | 没有明确方案 | 写清楚改什么怎么改 |
| 不写接口变更 | 怕麻烦 | 接口变更必须写 |
| 跳过用户确认直接编码 | 替用户做决定 | 必须等确认 |

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| 「这个改动很小，不用写设计书」 | 改动不分大小。改了什么就必须记什么 |
| 「我先写代码，设计书后面补」 | 后面不会补。先出设计书再动手 |
| 「需求已经很明确了」 | 明确 ≠ 写下来了。写下来才会发现漏了什么 |
| 「实际上更简单的做法是…」 | 如果有更简单的方法，写进设计书让开发者确认 |
| 「这个功能跟之前那个一样」 | 把「一样」的地方和「不一样」的地方都写出来 |

## 为什么重要

- 没有设计书 → 不知道代码要改成什么样 → 写偏了 → 返工
- 没有设计书 → 验收没依据 → 做完了不知道对不对
- 没有设计书 → 下一个人看不懂为什么这么改

**写设计书的 10 分钟，省的是后面几个小时的返工。**
