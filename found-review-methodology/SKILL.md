# 审查方法论

## 核心原则

**审查者和执行者必须是不同的人。上下文必须是干净的。**

这不是形式主义——连续的对话会让审查者不自觉地承接执行者的思路和偏见，失去客观性。

---

## 流程

```
当需要审查任何内容（设计书、代码、测试、配置等）时：

1. 评估审查范围：需要审什么？（哪份设计书？哪个模块的代码？）
2. 整理前置信息：要告诉审查者什么？
   → 只包含客观事实：文件位置、项目背景、技术栈
   → 不包含：
      ❌ 「我觉得这个实现有点问题，你帮我看看」
      ❌ 「这个功能比较复杂，小心点」
      ❌ 「之前我们讨论过要改成 X 方案」
      ❌ 任何自己的判断、猜测、顾虑
3. 生成审查任务：把前置信息打包，派子 agent（sessions_spawn mode=run）
4. 审查完成后取回结果
5. 如果子 agent 提出问题和建议 → 独立评估，不受自己预设的干扰
```

## 前置信息模板

```markdown
## 审查请求

### 审查对象
{要审查的文件或功能}

### 项目背景
{技术栈、项目阶段、相关模块（只说事实）}

### 审查重点（可选）
{如果有特定关注点可以说，但必须具体且客观：
「检查 SQL 注入防护」✅
「看看有没有安全问题」❌ — 太宽泛，引导审查者往安全方向想}
```

## 不允许的内容

```
❌ 自己的判断：「我觉得这个设计有问题」
❌ 预设结论：「这样改可能会导致 X 问题」
❌ 个人偏好：「我不太喜欢这种写法」
❌ 对话历史：「之前我们讨论过」
❌ 情感色彩：「这个比较简单」「这个很复杂」

允许的只有：
✅ 事实：「文件在 src/api/upload.py」
✅ 上下文：「这个模块是处理用户上传的，会暴露在公网」
✅ 客观要求：「请检查是否有 SQL 注入风险」
```

## 防止上下文污染

派审查子 agent 时，除了提供客观前置信息，还必须显式声明：

> **「这是一个全新审查。不要读取你的记忆文件、日记或任何历史记录。从头开始看。」**

**「记忆」的精确界定：**
- 禁止读取的是子 agent 的**个人长期记忆**（MEMORY.md、diary/ 下的日记、历史对话记录）
- **不禁止**读取项目的**规约文件**（.tws/ 下的 coding-conventions.md 等）——这些是审查时需要了解的上下文
- 如果子 agent 的系统配置中有自动加载记忆的流程（如 AGENTS.md 要求「每次醒来先读 MEMORY.md」），
  应在 spawn 参数中指定 `context:"isolated"` 保证隔离，而不是只依赖文字声明

这是为了防止子 agent 被之前的对话记录或自己的记忆文件污染，导致审查带有预设偏见。

> 即使你作为主 agent 觉得「我跟她说过应该没问题」——子 agent 自己的记忆仍然可能包含之前轮次的信息。明确声明「从头开始」才能保证每次审查的独立性。

---

## 为什么

```
- 连续对话中的审查 → 审查者的判断被执行者的思路污染
- 有引导性的前置信息 → 审查者的注意力被定向，错过真正的问题
- 干净的上下文 → 审查者只能依赖自己的判断，这是真正独立的审查

我们让小念做了多轮 review，每轮新开子 agent 的效果都更好。
不加引导能发现真正的问题。
加了引导的她反而会去找你提的方向。
```

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| 「这个改动很小，我看着就行，不用开子 agent」 | 即使自己看，也建议切换到新上下文再读一次 |
| 「不加引导的话她可能抓不住重点」 | 抓不住重点说明你的前置信息没给够事实，不是不够引导 |
| 「开子 agent 太麻烦了」 | 一次干净的审查比三次被污染的重审更快 |
| 「我跟她说了我的想法，她可以在此基础上补充」 | 补充 = 拓展你的偏见，不是独立意见 |
