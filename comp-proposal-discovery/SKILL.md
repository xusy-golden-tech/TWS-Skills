# 需求澄清

## 核心原则

**没澄清就设计 = 做的是自己的假设。**

客户说"我要一个管理系统"和真正需要的之间，隔着一层你必须挖出来的东西。这一步的任务就是把模糊需求变成可验证的输入。

## 定位

本 skill 既可在 `flow-build-solution` 中作为第 1 步由子 agent 加载，也可单独调用——当你只需要梳理需求、还未进入方案设计阶段时。

## 输入来源验证

手头可能有的材料：

| 输入类型 | 信息密度 | 重点是 | 注意事项 |
|---------|---------|--------|---------|
| RFP/招标文件 | 高 | 逐条提取，标出矛盾 | RFP 可能是多个部门拼凑的，内部可能自相矛盾 |
| 会议记录/语音转写 | 中 | 从对话中抽取需求，标注说话人 | 不同角色说的可能不是一回事 |
| 客户一句话需求 | 低 | 追问，不能硬推测 | 一句话需求 = 信息缺口列表就是产出 |
| 竞品/参考系统 | 偏低 | 理解"他们想要什么效果" | "和 XX 一样" ≠ 照抄，要追问"哪里一样哪里不同" |

如果材料不足以支撑分析，输出以信息缺口为主——不要为了凑输出而编造需求。

## 子能力

### A. 需求提取

从原始材料中逐条抽取，不做判断、不合并、不归纳：

```
单条需求的粒度：
❌ "需要一个完整的管理系统" — 太粗，拆
❌ "需要用户管理、权限管理" — 还行，但还能拆
✅ "需要用户注册、登录、密码找回" — 合理粒度

规则：
- 一条需求只描述一个能力
- 保留客户原话（或标注为归纳）
- 标注来源（哪份材料、谁说/写的）
- 标注确定性：明确说的 / 推测的 / 存疑的
```

**为什么这个粒度：** 合并需求会隐藏信息——"用户管理和权限管理"是不是一回事？拆开才能验证。

### B. 需求分类

将提取出的需求按性质分类，这是后续方案设计中架构划分的种子：

```
分类维度（选最匹配的，不必全部用）：

功能需求：系统要做什么
非功能需求：性能/安全/可用性/扩展性
业务需求：客户为什么需要（背后的商业目的）
约束条件：限制条件（时间/预算/技术栈/合规）

优先级（客户感知的优先级，不是你能判断的"实现优先级"）：
- 必须做（没有 = 不验收）
- 应该做（没有 = 体验差但不影响验收）
- 可以延后（第一版可以没有）
- 待确认（不确定客户是否真要）
```

**为什么分类：** 不做分类的需求清单 = 一堆平级待办项。分类后方案设计者知道把架构重心放哪。

### C. 潜在需求挖掘

客户没说不代表不需要。按行业常识主动检查：

```
检查清单（按项目类型选）：

□ 权限和角色：谁操作？不同角色看到的一样吗？
□ 数据迁移：旧系统数据要搬吗？格式是什么？
□ 部署/运维：谁部署？谁维护？维护多久？
□ 培训/文档：客户需要培训吗？文档中英文？
□ 合规：行业有无特殊规定？（医疗/金融/政务）
□ 对接：要和什么现有系统交互？接口格式？
□ 多语言/多区域：只服务一个语言/一个地区？
□ 灾备：数据备份策略？宕机容忍度？
□ 审计/日志：需要对操作留痕吗？
□ 组织变更：客户方如果换了对接人会怎样？
```

**为什么预埋：** 这些不是"后期需求变更"，是你方案设计时就该预留的。到开发阶段再补 = 返工。

### D. 冲突检测

客户需求里可能藏了自相矛盾的点：

```
典型模式：
"既要快又要便宜又要好" → 三角不可能同时满足，确认真正优先级
"和 XX 系统一样就行" → "一样"通常只指某些部分，追问具体是哪部分
"先做出来看看" → 范围无边界，要求客户给出"看看"的判定标准
"X 功能很重要"但描述很模糊 → 追问 X 解决了什么业务问题
"这个简单，顺便做一下" → 没有"顺便"的功能，每个功能都有成本

检测方法：
1. 列出所有表述模糊的需求
2. 列出逻辑上不可能同时满足的组合
3. 每个冲突点转化为一个待确认问题
```

**为什么检测：** 带着矛盾的输入做方案，最后总有一个矛盾方不满意。越早暴露越便宜。

### E. 范围界定

把模糊描述变成清晰边界：

```
明确三件事：
- 本次做：{具体功能/能力范围，用可验证的语言描述}
- 本次不做：{明确排除的内容 + 排除原因}
- 待定：{取决于 X 条件，X 确认后再定}

"不做"的写法：
❌ "暂时不做的功能" — 太模糊
✅ "本次不包含数据迁移（客户未提供旧系统数据结构，当前不可估）"

好的"不做"条目包含：
- 什么不做
- 为什么不做的原因
- 什么时候可能做（如果适用）
```

**为什么最关键：** 范围边界是方案评审的第一参照物。方案做了超出范围的东西 = scope creep；漏了范围内的东西 = 遗漏。两种都致命。

### F. 约束识别

从原始材料中提取所有限制条件，约束决定方案的可行解空间：

```
□ 时间约束：硬 deadline 还是期望？延迟的代价是什么？
□ 预算约束：总包还是分项？含不含硬件/第三方？
□ 技术栈约束：必须用/不能用什么？原因是技术原因还是甲方偏好？
□ 合规约束：是否需要等保/密评/GDPR？谁来承担合规成本？
□ 组织约束：客户方谁拍板？验收标准谁定？
□ 依赖约束：客户需要先完成什么你才能开工？
□ 部署约束：私有化/公有云/混合？客户提供服务器还是你提供？
```

**为什么重要：** 约束 = 方案设计师的边界线。不了解约束 = 在笼子外面做方案 = 方案可能根本不可行。

## 决策判断

以下情况直接输出信息缺口，不进入下一步：

```
□ 需求描述全是愿望没有具体功能（"我们要做一个牛逼的系统"）
□ 关键约束全部缺失（没时间没预算没技术栈 → 方案不可设计）
□ 一个以上的核心需求互相矛盾且客户未澄清
□ 材料的来源和可信度本身存疑（第三方转述、过时的 RFP）
```

以下情况可以推进但有风险标注：

```
□ 需求完整但约束偏松（大预算宽时间 → 提醒可能 scope creep）
□ 客户明确说"先大致估计"（标注：以下均为初步范围，报价时需加缓冲）
□ 部分需求依赖客户提供的信息但客户还没给（标注：后续信息变化 = 方案需调整）
```

## 输出格式

```markdown
## 需求摘要

### 项目概述
{用客户的语言，一句话说清楚这是什么项目}

### 显性需求
| # | 需求 | 分类 | 来源 | 确定性 | 优先级 |
|---|------|------|------|--------|--------|
| 1 | 用户可注册、登录、找回密码 | 功能 | 会议记录 P3 | 明确 | 必须 |
| 2 | 响应时间 < 2 秒 | 非功能 | RFP §3.2 | 明确 | 必须 |

### 潜在需求（客户未提出但可能需要的）
| # | 需求 | 触发原因 | 建议处置 |
|---|------|---------|---------|
| 1 | 老系统数据迁移 | 现有系统截图表明已有数据 | 请客户确认旧系统数据量和格式 |

### 冲突点
| # | 冲突描述 | 涉及需求 | 转化问题 |
|---|---------|---------|---------|
| 1 | RFP 要求 3 个月交付但功能列表需要 20 人月 | R1,R4 | 请确认：缩减范围还是延长时间？ |

### 范围边界
- 本次做：{具体范围}
- 本次不做：{排除项，每条附原因}
- 待定：{附条件}

### 约束条件
| 类型 | 约束内容 | 来源 | 刚性（硬/软） |
|------|---------|------|-------------|
| 时间 | 9 月 30 日前上线 | RFP §1 | 硬（合同有罚则） |
| 技术 | 必须用 Java，因客户内部维护团队只懂 Java | 会议记录 | 硬 |

### 信息缺口
{按对方案设计的影响程度排序：}
1. {缺口} — {为什么这个信息重要} — {建议获取方式}
2. ...

### 完整性评估
{选择一项：}
- 可直接进入方案设计（信息充分，无需补充）
- 可进入方案设计但有风险标注（见上）
- 建议先补齐信息缺口再进入方案设计（列出最少需要补齐哪些）
```

## 常见失败模式

| 表现 | 根本问题 | 正确做法 |
|------|---------|---------|
| 客户说什么就记什么 | 没挖掘潜在需求 | 按检查清单逐项过，全部标注 |
| "这个需求很明确" | 把模糊当明确 | 用具体问题验证，不说清楚不放过 |
| 范围不写"不做" | 怕限制自己 | 不做的边界 = 后续评审的保护网 |
| 推测需求标注为"明确" | 把猜测当事实 | 确定性一栏如实标注，推测的来源不能写"客户说的" |
| 需求太粗 "建一个 XX 系统" | 没拆到可验证粒度 | 逐条拆到单一能力 |
| 遇到冲突绕过 | 觉得"后面再说" | 冲突 = 现在要确认的问题，不是后面的事 |

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| "客户需求写得很清楚了" | 客户写的 ≠ 客户真正需要的。你还没开始检查清单 |
| "这些潜在需求太细节了，后面再说" | 后面就是方案重做。预埋的成本是 0，补丁的成本是返工 |
| "先按我的理解出方案" | 理解的偏差在方案阶段会被放大 10 倍。现在花 10 分钟核实比花 10 小时返工便宜 |
| "需求和方案差不多，一起出了吧" | 需求没锁定就设计 = 对着移动靶射击 |
| "信息不够但可以合理推断" | 推断 = 假设。你必须标注这是推断，不是事实 |
| "范围边界写太多'不做'客户会不高兴" | 客户不高兴是现在的事。不写 = 出问题时你没依据 |
