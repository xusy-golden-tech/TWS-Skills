# 文档/代码拆分

## 核心原则

**上下文是有限的。一个文件太长 = agent 加载它的代价太高。**

拆分的目的是让每个文件在加载时能在上下文里留下足够空间给其他信息。

---

## 拆分的触发条件

### 设计书触发拆分

```
建议拆分：
- 一个设计书覆盖了 3 个以上独立模块 → 拆成每模块一本
- 行数超过 200 行 → 考虑拆分
- 包含的场景太多（正常、异常、边界各 5+ 条）→ 拆出独立场景文档
- agent 加载后抱怨上下文不够用 → 说明太长了，必须拆

如果设计书的长度主要是由接口定义表格导致的（不是逻辑描述），
可以考虑把接口定义独立成单独的接口文档，设计书本身保持精炼。
```

### 代码触发拆分

```
建议拆分：
- 一个文件超过 300 行 → 考虑拆（标准 SRP）
- 一个类／函数有多种职责 → 拆成多个类/函数
- 同一个文件里既有工具函数又有业务逻辑 → 拆
- 测试文件和生产代码混在一起 → 拆成独立的测试文件
```

---

## 拆分标准

```
好的拆分 → 拆完后每个文件能独立理解（不需要读了 A 才能读 B）
不好的拆分 → 拆成了碎片，读 A 时频繁跳到 B 又跳到 C

检查方法：拆完后，从头到尾读一份文件，如果频繁出现「见 xx 文件」= 拆太碎了。
```

---

## 代码拆分后的设计书

```
代码拆分后，设计书必须同步更新：

1. 如果代码从一个文件拆成多个文件：
   → 更新设计书中的「涉及文件」列表
   → 添加文件结构说明（拆成了什么结构，为什么这么拆）
   → 保持设计书逻辑完整，不要跟着代码一起拆散

2. 设计书不应该因为代码拆了就跟着拆：
   → 设计书是按「功能」组织的，不是按「文件」组织的
   → 代码拆了但功能还在同一模块 → 设计书只需要更新文件路径
   → 代码拆到了新的模块 → 设计书跟着分拆

3. 拆后验证：
   → 新读者读了设计书后，能快速定位到具体代码文件
   → 新 reader 读了代码后，能通过设计书理解整体意图
```

---

## 拆后的上下文优化

```
拆分完成后：
1. 检查：最高频加载的几个文件是否都控制在合理范围内
2. 如果有文件仍然太长 → 继续拆
3. 运行 `tws-graph lint` 验证 skill 文件结构完整性
```

---

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| 「这个文件还能看，不用拆」 | 你觉得能看的文件，agent 下次加载时可能嫌太长 |
| 「拆了文件还要改设计书，麻烦」 | 拆不改设计书 = 设计书滞后，比不拆还糟 |
| 「先写在一起，后面再拆分」 | 后面不会拆。一开始就按模块分开 |
