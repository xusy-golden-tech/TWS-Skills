# 审查结果分类

## 问题分类

主 agent（项目经理）收到审查报告后，必须做分类判断：

```
子 agent 提出的问题 → 主 agent 分类
├── A 类（硬伤/功能bug/逻辑错误）→ 必须修
│   「这个接口参数写错了」「这段逻辑无法编译」
│   「这里忘了处理空值」「这个边界条件没覆盖」
│
├── B 类（设计取舍/风格偏好/优化建议）→ 主 agent 决定是否修
│   「这段代码可以更简洁」「命名不够直观」
│   「可以用更优雅的方式实现」「建议重构这部分」
│   「这个实现跟 XXX 风格不一致」
│
└── C 类（重复/已知/首次提过但已经讨论过）→ 跳过
    「上次提过的同类问题又出现了」（说明是设计选择）
    「这个之前讨论过决定保持现状」
```

## 叫停标准

如果出现以下情况，主 agent 应主动叫停审查循环，进入下一阶段：

1. **连续 N 轮审查都在提 B 类问题**（N≥2）——说明审查者已经找不到硬伤了，再迭代下去只是不同口味的反复
2. **审查报告与上一轮高度重叠**——子 agent 在重复说同一类问题
3. **修改成本 > 潜在收益**——改一个 B 类问题需要改动多个模块，但只是「更好看」
4. **进度压力**——用户明确说了时间紧，先交付

## 叫停后的操作

```
决定叫停时：
1. 汇总所有未采纳的审查意见
2. 写入 .tws/deferred-issues.md（以后有空再处理的 backlog）
3. 继续下一阶段
4. 如果未来某个审查又提到同样的问题，从 deferred-issues 里捞出来重新评估
```

## 子 agent 失败/超时处理

```
子 agent 报告失败或超时 →
1. 分析原因
   ├── 任务描述不清 → 重新描述再派
   ├── 缺少访问权限/环境问题 → 标记为环境阻塞，上报开发者
   ├── 模型幻觉/执行错误 → 重新描述范围更小的任务再派
   └── 任务本身不可行 → 回退到上一阶段重新设计
2. 重试策略
   - 同一个子 agent 最多重试 2 次
   - 2 次后仍失败 → 切换到更小的任务粒度重新派
   - 换成更小的任务后如果还是失败 → 上报开发者，停止推进
3. 失败不影响已完成的并行任务
   - 已完成的任务保留结果
   - 失败的任务标记在 checkpoint 中
   - 等开发者修复阻塞后重新派
```
