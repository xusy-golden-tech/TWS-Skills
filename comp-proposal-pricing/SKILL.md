# 报价方案

## 核心原则

**报价绑定方案，每一个数字都有出处。**

方案说 3 个模块报价只算 2 个 = 漏估。方案没提到的模块报价却有 = 你替客户做决定了。两种情况都不可接受。

## 前置输入

- 方案文档（已通过评审锁定——不要给未锁定的方案报价）
- 需求摘要中的约束（预算范围、付款条件偏好）

## 子能力

### A. 人力估算

这是报价的核心。估偏了 = 项目亏损或报价虚高失去竞争力。

#### 估算方法：逐模块、逐角色

```
| 模块 | 角色 | 人天 | 依据（绑定方案的哪一节） | 复用/参考 |
|------|------|------|------------------------|---------|
| 用户中心 | 后端 | 5 | 方案 4.1 — 3 个 API（注册/登录/权限） | 权限中间件可复用现有组件，省 1 天 |
| 用户中心 | 前端 | 3 | 方案 4.1 — 4 个页面（注册/登录/密码找回/个人资料） | |
| 用户中心 | 测试 | 2 | 功能测试 + 兼容性 | |
```

#### 人天包含项

每个人天必须包含：

```
编码 + 自测 + 联调 + Code Review 修改 + 文档

如果不含测试（有独立 QA），标注"开发人天"并在其他项中列出测试人天。
不含项目管理——项目管理和沟通在"管理系数"中另算。
```

#### 人天不含项（容易被忽略的）

```
这些项不是某个模块的工作，但是项目必需的：

□ 环境搭建/脚手架（项目初始化的固定成本）
□ 部署/CI/CD 配置
□ 数据迁移脚本（如有旧数据）
□ 性能测试/安全测试（如果客户要求）
□ 上线支持
□ 培训/文档（如果是交付物的一部分）
□ Bug 修复缓冲（通常是开发人天的 10-15%）
```

#### 管理系数

```
项目管理、客户沟通、需求确认、进度汇报：
- 简单项目（< 3 个月、单一对接人）：开发人天 × 1.1-1.15
- 中等项目（3-6 个月、多方利益相关者）：开发人天 × 1.15-1.2
- 复杂项目（> 6 个月、多层审批、驻场）：开发人天 × 1.2-1.25
```

#### 不确定性缓冲

```
基于方案的假设数量调整缓冲：

假设 ≤ 2 个：开发人天 × 1.1
假设 3-5 个：开发人天 × 1.2
假设 > 5 个：开发人天 × 1.3-1.5（并且请标注"高不确定性——建议固定总价之外加浮动条款"）
```

**为什么按假设数调缓冲：** 方案评审已经标注了假设。假设越多 = 方案变更概率越高 = 需要预留更多余地。这是定量化的风险管理，不是拍脑袋。

### B. 第三方服务估算

```
逐项列出所有外部依赖的费用：

| 服务 | 用途 | 规格 | 单价 | 周期 | 小计 | 依据 |
|------|------|------|------|------|------|------|
| 云服务器 | 应用部署 | 4C8G × 2 | ¥500/月 | 12 月 | ¥12,000 | 方案 2 — 阿里云 ECS |
| SMS | 验证码 | 国内短信 | ¥0.045/条 | 预估 3 万条 | ¥1,350 | 预估日均 100 条 × 300 天 |

注意：
- 第三方服务费用标注是报价还是客户直接采购（如果是客户采购，报 0 但标注"客户自付"）
- 第三方服务的价格会变动，标注"价格以实际采购时为准"
```

### C. 定价模型选择

乙方的常见定价模型，不是 SaaS 的 tier/freemium：

```
| 模型 | 适用场景 | 风险归属 | 本项目匹配度 |
|------|---------|---------|-------------|
| 固定总价 | 范围明确、需求不可变 | 风险在乙方（估算偏差自己扛） | |
| 人天 × 单价 | 范围模糊、探索性工作 | 风险在甲方（多做了多付） | |
| 里程碑固定价 | 长周期、按阶段交付 | 阶段性风险在乙方 | |
| 固定 + 浮动 | 核心固定 + 变更人天结算 | 风险共担 | |
| 月费/季度费 | 持续服务（运维/运营） | 期限风险在甲方 | |

推荐模型：{选一项} — {理由绑定项目特点，而非个人偏好}

如果是固定总价：必须定义变更流程——什么算变更、按什么计价。
如果是人天结算：建议设上限保护——"不超过预估的 120%"之类。
```

### D. 付款节奏

```
付款节奏的作用：保护现金流 + 控制交付风险

推荐结构：

| 节点 | 比例 | 触发条件（必须可验证） |
|------|------|---------------------|
| 签约 | 20-30% | 双方签署合同 |
| 里程碑 1 | 对应比例 | {用方案中该里程碑的验收标准} |
| 里程碑 2 | 对应比例 | {同上} |
| 终验 | ≥ 10% | 全部交付物验收通过 + 源码/文档移交 |

规则：
- 签约款 ≥ 20%：让客户有成本感，不会随意变更需求
- 终验款 ≥ 10%：最后的交付保障。如果尾款太少，客户不验收你也没辙
- 里程碑触发条件用方案中的验收标准——保持一致，不要说另一套话
```

## 常见失败模式

| 表现 | 根本问题 | 正确做法 |
|------|---------|---------|
| 人天按"感觉"拍 | 不看方案的模块拆解 | 逐模块估算，每个数字对应方案中一个模块 |
| 忽略项目管理和沟通成本 | 只算了编码人天 | 加管理系数 |
| 不设缓冲或缓冲一律 10% | 没根据不确定性调整 | 按假设数量定缓冲比例 |
| 定价模型只选固定总价 | 习惯思维 | 分析项目特征后选，附理由 |
| 尾款 < 10% | 没考虑验收保护 | 尾款是最后保障，不能太少 |
| 不写不包含项 | 怕显得限制多 | 不写 = 以后扯皮你说不清 |

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| "人天大概估一下就行" | 报价人天 = 执行基准。估偏了要自己吃 |
| "先报低点拿下项目，后面再补" | 后面补不回来。客户认的是报价，不是你的解释 |
| "不包含项不写了，显得限制太多" | 没写的限制 = 法律上不存在。出事了你没依据 |
| "缓冲加太多了报价显高" | 报价高丢一个项目 vs 报价低赔一个项目。你选哪个 |
| "管理沟通成本不算了，我们自己扛" | 10-20% 的管理成本不是"扛"，是项目真实成本 |
