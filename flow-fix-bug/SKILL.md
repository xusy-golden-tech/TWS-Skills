# 修复 Bug

> **与热修复（hotfix）的区分：**
> - `fix-bug` 走完整质量流程（方案确认→回归→防复燃），适用于**日常开发/非紧急** Bug
> - `hotfix` 跳过方案确认和集成测试，适用于**生产环境紧急**问题
> - 入口 skill 自动判断：用户说「紧急」「hotfix」→ 走 hotfix；否则走 fix-bug
> - 如果走 fix-bug 简化路径后发现时间仍然不够 → 建议用户考虑改走 hotfix

## 复杂度门禁（第 0 步）

```
检查条件：
□ 只改一行或一个表达式？
□ 不改模块结构、不改接口？

全部满足 → 简化路径
任一不满足 → 完整路径
```

如果仅凭用户描述无法确认“只改一行/一个表达式”且“不改模块结构、不改接口”同时成立，默认走完整路径；只在确认成本很低时问一个澄清问题。

### 简化路径（小修复）

```
根因 → 修复 → 验证 → 同步
省略完整路径中的方案确认、完整回归、防复燃、集成测试；不省略根因、验证和同步
```

### 完整路径

```
复现 → 根因 → 方案 → 方案架构校验 → 修复 → 回归 → 代码审查 → 防复燃 → 影响评估 → 集成 → 同步
```

## 完整路径

### ① 复现

子 agent 通过 Skill 工具加载 `comp-reproduce`

```
1. 确认 Bug 现象
2. 找到复现步骤
3. 验证重现 → 记录
```

### ② 根因分析

子 agent 通过 Skill 工具加载 `comp-root-cause-analysis`

```
定位到具体位置 → 分析原因 → 评估影响
```

### ③ 修复方案

```
1. 怎么修？改哪里？
2. 有没有副作用？
3. 这个修法是在解决问题还是在掩盖症状？
   - 如果修法是加 patch/flag/workaround → 能不能从根上修？
   - 如果是在已有的 hack 上再叠逻辑 → 先清理再修
4. 修复是否引入新的耦合或技术债？
5. 确认后再动手
```

### ③.5 方案架构校验

独立子 agent 执行（使用干净上下文，不读执行者的对话历史）：

```
审查修复方案，逐项检查：

□ 耦合检查：修复是否引入了对其他模块的新依赖？如果有，是必要的还是图方便？
□ 屎山检查：是否在已有 hack/workaround 上继续叠加逻辑？如果是，有没有更干净的修法？
□ 扩展性检查：这个修法如果将来需求变了，是容易改还是得推翻重来？
□ 一致性检查：修复风格与项目现有架构一致吗？有没有破坏既有的抽象层次？
□ 归属检查：修复逻辑放在了正确的位置吗？还是散落在不该放的地方？

输出结论：
- 通过：方案在架构层面没问题
- 有风险：具体列出风险点 + 建议的替代方案
- 阻塞：方案本身就是在制造技术债，必须换方案
```

此步骤是轻量检查，不需要加载独立 skill。主 agent 在派审查子 agent 时直接附上以上检查清单。
审查结论为"有风险"时，主 agent 决定是否调整方案；结论为"阻塞"时，必须回到③重新设计。

### ④ 修复

子 agent 通过 Skill 工具加载 `comp-implementation`（最小改动模式）

```
1. 实施修复
2. 验证 Bug 不再复现
```

### ⑤ 单元+回归

子 agent 通过 Skill 工具加载 `comp-test`

```
链式验证 → 检查修复已完成

1. 跑相关测试
2. 检查连锁影响
```

### ⑥ 代码审查

独立子 agent 通过 Skill 工具加载 `comp-code-review`

```
派独立子 agent 审查修复代码：
□ 修复逻辑是否正确？有没有遗漏的边界情况？
□ 有没有引入新问题？
□ 测试是否覆盖了修复点？
□ 符合代码规约吗？
```

### ⑦ 防复燃（原⑥）

```
这个 Bug 是孤例还是某类问题？
同类问题可能在哪出现？
要加什么防护？
```

### ⑧ 影响评估（原⑦）

子 agent 通过 Skill 工具加载 `comp-impact-assessment`

```
如果修复涉及跨模块影响，评估连锁范围。
```

### ⑨ 集成测试（原⑧）

子 agent 通过 Skill 工具加载 `comp-test`（集成验证范围）

```
链式验证 → 检查所有任务完成

跨模块连锁影响检查。
```

### ⑩ 同步（原⑨）

子 agent 通过 Skill 工具加载 `comp-design-sync`

## 简化路径（小修复）

```
1. 根因 → 找到位置
2. 修复 → 改代码
3. 验证 → Bug 不再复现 + 跑核心测试
4. 同步 → 设计书同步

简化路径省略完整路径中的方案确认、完整回归、防复燃、集成测试。
但「验证」和「同步」不能省略——必须确认 Bug 不再出现，并记录设计书变更。
```

标准完成依据见根目录 `checkpoint-reference.md`。

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| 「先改了再找根因」 | 没有根因就无法判断修复是否完整 |
| 「复现不了也能修」 | 复现不了就没有可靠的通过标准 |
| 「小修复不用防复燃」 | 小 bug 常来自系统性缺口，至少要判断是否需要防复燃 |
