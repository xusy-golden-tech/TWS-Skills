# TWS — 目标驱动自主执行（Goal Mode）

## 这是什么

`using-tws-goal` 是 `using-tws` 的目标驱动增强版。给一个目标，agent 自己搞定全部：判断场景 → 拆分阶段 → 设门禁 → 写测试 → 定验收标准 → TDD 循环推进 → 达成目标。

**与 `using-tws` 的核心差异：**

| 维度 | using-tws | using-tws-goal |
|------|-----------|----------------|
| 驱动方式 | 步骤确认驱动 | 目标驱动，自主推进 |
| 用户交互 | 每步确认 | 初始确认后全自动 |
| 门禁/测试/验收 | flow skill 内隐式 | 显式写入 spec 文件，逐项勾销 |
| 循环机制 | 无 | TDD 闭环：门禁 → 实现 → 测试 → 验收 → 下一阶段 |
| Bug 处理 | 主 agent 判断 | 分流：阻塞 → spec / 非阻塞 → KNOWN_ISSUES.md |
| 压缩恢复 | 无 | 读 plan + spec 恢复状态，不依赖记忆 |
| 方案标准 | 默认 | 根源解决 + 优雅，不考虑工数和工期 |

**适用场景：**
- 「接下来我人不在了，靠你自己解决所有问题」
- 长期自主任务（多阶段、多文件、需要持续决策）
- 需要 spec 驱动 + TDD 保障质量的场景
- 上下文可能被压缩的长流程

## 全局规则

不猜测。判断 → 计划 → 执行 → 验证 → 循环。

### 继承自 using-tws 的基础规则

1. 没有设计书就不写代码
2. 增量实施，每步可验证，禁止跳过
3. 测试通过是最低要求，还要检查边界和同步
4. 改了代码必须同步设计书，不改 = 没改完
5. **主 agent 不写代码** — 所有编码、测试、同步由子 agent 执行（详见 `comp-subagent-dispatch`）
6. **主 agent 不加载 comp skill** — comp skill 是给子 agent 的工作手册。主 agent 的职责是派子 agent、告诉它加载哪个 comp skill、验收产出
7. **所有改动必须从 develop 开新分支** — `git checkout develop && git checkout -b {type}/{description}`（详见 `found-branch-flow`）
8. **子 agent 完成后必须 git commit** — 每完成一个子任务立即 commit（不 push），防止后续子 agent 误操作回滚已验收的改动
9. **主 agent 关注上下文容量** — 长流程中自检：已派 5+ 子 agent / 汇报累积超 3 屏 / 下一个任务很复杂。偏重时减少汇报内联、考虑合并后续步骤；过载时 checkpoint 保存

### Goal Mode 专属规则

10. **阶段门禁制** — 每个执行阶段开始前，在 spec 文件中明确三项：**门禁条件**（什么情况下可以开始这个阶段）、**测试用例**（如何验证正确性）、**验收标准**（什么算完成）。执行中实时更新状态，完成时逐项勾销。不设门禁就开始 = 裸奔
11. **TDD 闭环推进** — 每个阶段的执行顺序：先写失败测试 / 验收条件 → 实现使其通过 → 验证 → 更新 spec → 进入下一阶段。循环直到 spec 中所有阶段的验收标准全部满足。禁止跳过测试先写实现
12. **压缩恢复协议** — 每次上下文压缩后，第一时间读取 plan 文件和 spec 文件，从中恢复当前阶段、进度和下一步行动，不依赖记忆。spec 是外脑，压缩不会丢
13. **Bug 双向分流** — 执行中遇到的 bug 必须在 spec 中判断分流：
    - **阻塞级**（当前阶段无法继续 / 核心功能无法工作 / 数据安全风险）→ 追加到 spec 文件，成为新的验收项，TDD 解决
    - **非阻塞级**（不影响当前阶段推进 / 边缘 case / 优化建议）→ 记入项目根目录 `KNOWN_ISSUES.md`，标注发现阶段和原因，目标达成后统一处理
14. **方案铁律** — 选择方案时不考虑工时和工期。唯一判断标准：能否从根源解决问题（而非掩盖症状），解法是否优雅（无垃圾代码、无硬编码、无投机性抽象）。如果两个方案都能解决，选更优雅的那个；如果一个只是"快点修好"，选另一个

## 执行流程

### 第一步：接收目标，创建 spec 文件

用户给出目标后，不急着执行。先做三件事：

**1a. 解析目标**

从用户描述中提取：
- 目标是什么（一句话）
- 约束条件（技术栈、时间、兼容性等）
- 隐含需求（用户没说但显然需要的）

如果信息不足以判断场景，追问 1-2 个问题，但不过度追问。

**1b. 创建 spec 文件**

用 Write 工具创建 `.tws/goal-specs/{goal-short-name}.md`，填入初始模板（模板见下方「Spec 文件规范」）。

此时 spec 中「元信息」和「总体目标」已填充，阶段列表待第二步场景路由后补充。

**1c. 创建 session 文件**

用 Write 工具创建 `.tws/sessions/{flow-type}-{short-desc}.md`，标注特殊模式为「Goal Mode」。

### 第二步：场景路由

此步骤复用 `using-tws` 的场景判断逻辑：

**硬边界：此步骤只做判断，不做调查。**

```
允许：
✅ 读取 .tws/ 下的状态文件
✅ 根据用户描述判断场景类型
✅ 追问 1-2 个问题明确场景

禁止：
❌ 读业务代码
❌ 搜索代码库
❌ 起子 agent 去调查
❌ 「我需要先了解一下才能判断」→ 不需要
```

先检查是否有未完成的流程：

```
用 Glob 检查 .tws/sessions/*.md：
→ 有未完成的目标流程 → 「检测到上次未完成的目标（{目标名}），进度到 {当前阶段}。要续上吗？」
  → 用户选「是」→ 读取 spec + session，从断点续上
  → 用户选「否」→ 开始新目标
```

然后根据场景特征判断流程：

| 特征关键词 | 流程 | 说明 |
|-----------|------|------|
| 「紧急」「hotfix」 | hotfix | 时间紧、生产环境 |
| 「坏了」「报错」「不 work」「行为不对」 | fix-bug | 现有功能出问题 |
| 「新建」「从零」「脚手架」 | new-project | 空项目 |
| 「重构」「重写」「优化」 | refactor | 不改功能只改结构 |
| 「查一下」「为什么」「排查」 | investigate | 只查不修 |
| 「方案」「报价」「做方案」「出方案」「提报价」「PPT」「展示」「投标」「售前」 | build-solution | 做方案/报价/展示 |
| 「文档」「README」 | documentation | 产出物是文档 |
| 其他 / 不明确 | add-feature | 兜底 |

无法判断时追问 1-2 个问题，实在判断不定走 add-feature。

### 第三步：环境检查 + 加载 flow skill + 门禁判断

**3a. 项目索引是否就绪**

```
检查 .tws/project-map.md：
→ 存在 → 读取技术栈和路径映射
→ 不存在 → 走 using-tws 的初始化流程（调用 tws-init）

检查 tws-graph 可用性：
通过 Skill 工具加载 found-tws-graph-usage，按其中「前置检查」指引确认可用性
```

**3b. 加载对应的 flow skill，运行门禁判断**

直接用 Skill 工具按名称调用：

```
Skill(skill: "flow-fix-bug")
Skill(skill: "flow-add-feature")
Skill(skill: "flow-hotfix")
Skill(skill: "flow-refactor")
Skill(skill: "flow-investigate")
Skill(skill: "flow-new-project")
Skill(skill: "flow-documentation")
Skill(skill: "flow-build-solution")
```

从 flow skill 中获取复杂度门禁条件，判断走简化路径还是完整路径。

### 第四步：输出计划，等待确认（唯一一次确认）

基于 flow skill 的步骤 + goal mode 的 spec 驱动方式，输出完整执行计划。

**步骤不允许合并。** flow skill 中有几个步骤就展开几个，每步对应一条。

输出格式：

```
🎯 目标：【{目标描述}】
📋 场景：【{场景名}】
📐 流程：【{流程名}】（{简化路径 / 完整路径}，门禁依据：{为什么}）
📄 Spec 文件：.tws/goal-specs/{name}.md
🔄 模式：Goal Mode — 确认后全自动推进，直到目标达成或遇到无法自行解决的阻塞

执行计划：

阶段 N — {阶段名}
  门禁：{进入条件}
  产出：{产出物}
  执行：子 agent（通过 Skill 工具加载 {对应 comp skill}）
  测试：{测试策略}
  验收：{验收标准}

要开始吗？
```

**这是整个流程中唯一一次用户确认。** 确认后进入全自动模式，不再询问。

用户确认后：
1. 以上计划成为**已承诺的执行计划**
2. 用 Write 更新 spec 文件，拆入所有阶段的「门禁 / 测试 / 验收标准」
3. 更新 session 文件，将计划中的阶段写入进度区
4. **立即加载子 agent 调度规则**：`Skill(skill: "comp-subagent-dispatch")`
5. 进入 TDD 循环执行

### 第五步：Spec 驱动 TDD 循环（核心）

这是 goal mode 的核心执行引擎。每个阶段按以下模式推进：

```
┌─────────────────────────────────────────┐
│  阶段开始                                │
│  → 检查门禁：前置条件是否满足？           │
│    不满足 → 先解决前置（可能触发新 Bug）   │
│    满足 → 继续                           │
├─────────────────────────────────────────┤
│  1. 写测试 / 验收条件（RED）              │
│     子 agent 加载 comp-test，先写失败测试  │
│     更新 spec：测试用例状态               │
├─────────────────────────────────────────┤
│  2. 实现（GREEN）                        │
│     子 agent 加载 comp-implementation     │
│     使测试通过                           │
│     更新 spec：实现状态                   │
├─────────────────────────────────────────┤
│  3. 验证（REFACTOR + VERIFY）            │
│     运行测试确认通过                      │
│     检查边界条件                          │
│     检查设计书同步（如有）                 │
│     更新 spec：验收标准逐项勾销            │
├─────────────────────────────────────────┤
│  4. 阶段收尾                             │
│     git commit                           │
│     更新 spec：阶段状态 → ✅ 已完成        │
│     更新 session 文件进度                 │
│     → 进入下一阶段                        │
└─────────────────────────────────────────┘
```

**Spec 更新时机（硬规则）：**

子 agent 每次汇报后，主 agent 必须立即更新 goal-spec 文件，再派下一个子 agent。禁止攒到阶段结束再批量更新。

```
子 agent 汇报 → 主 agent 收结果 → 立即更新 spec → 再派下一个子 agent
                                  ↑
                          不可跳过，不可延迟
```

原因：spec 是 goal mode 的外脑。子 agent 的上下文每次都会释放，只有 spec 保留进度。spec 过期 = 后续子 agent 收到的任务背景可能基于错误的前置状态，导致任务错乱。

**循环终止条件：**
- spec 中所有阶段的验收标准全部 ✅ → 进入目标达成判定
- 遇到阻塞 bug → 追加到 spec，TDD 解决后继续
- 遇到无法自行解决的阻塞 → 停止，报告用户

**Bug 发现时的处理（在循环中随时触发）：**

```
发现 Bug
  ↓
判断：是否阻塞当前阶段？
  ├── 阻塞 → 追加到 spec「阻塞级 Bug」区
  │         → 成为新的验收项
  │         → 暂停当前阶段，先 TDD 修 Bug
  │         → 修完后回到原阶段继续
  │
  └── 不阻塞 → 记入 KNOWN_ISSUES.md
              → 标注：发现阶段、现象、不阻塞原因
              → 当前阶段继续
              → 目标达成后统一处理
```

### 第六步：目标达成判定

spec 中所有阶段验收标准 ✅ 后，进入终判：

**6a. 回溯验证**

加载 `comp-goal-verify`，从 spec 中的「总体目标」倒推，逐项检查：
- 目标是否真正在代码/产出物中达成？
- 有没有验收标准写了 ✅ 但实际没做到的？
- 有没有隐含需求被遗漏的？

方式：派子 agent（干净上下文），告诉它加载 `comp-goal-verify`，输入 spec 文件路径。

**6b. 终判**

```
验证通过 → 🎯 目标达成
  → 汇总：做了什么、关键决策、KNOWN_ISSUES.md 内容
  → 更新 spec 元信息：目标状态 → ✅ 已完成
  → 更新 session 文件：流程状态 → 已完成

验证不通过 → 回到第五步
  → 把遗漏项追加到 spec
  → TDD 解决
```

### 第七步：全局纠错

如果执行过程中发现理解错了目标或走错了方向：

```
发现走偏了 → STOP
1. 记录：为什么走偏了？（理解错了？信息不全？）
2. 纠正：回到正确的方向上
3. 更新 spec：修正目标描述或阶段定义
4. 更新 session：记录纠偏事件
5. 继续执行

走偏是正常的，不走出来才不正常。
```

## Spec 文件规范

### 位置

`.tws/goal-specs/{goal-short-name}.md`

### 模板

```markdown
# Goal: {一句话目标描述}

## 元信息
- 创建时间：{YYYY-MM-DD HH:MM}
- 关联 flow：{flow-xxx}
- 关联 session：.tws/sessions/{file}.md
- 关联分支：{branch name}
- 目标状态：⏳ 进行中

## 总体目标
{用户原始需求，保持原样。下方是结构化拆解}

{目标拆解：用户真正要的是什么？成功是什么样的？}

## 约束条件
- {技术栈约束}
- {兼容性约束}
- {时间/资源约束（如有）}

## 阶段 1: {阶段名}
### 门禁
- [ ] {进入此阶段的前置条件}
### 测试
- [ ] {测试用例 1}
- [ ] {测试用例 2}
### 验收标准
- [ ] {验收条件 1}
- [ ] {验收条件 2}
### 状态：⏳ 进行中

## 阶段 2: {阶段名}
...

## 阻塞级 Bug
<!-- 执行中发现的阻塞当前阶段的 bug，追加到此区域 -->

### BUG-001: {标题}
- 发现阶段：{阶段名}
- 发现时间：{timestamp}
- 复现步骤：{steps}
- 阻塞原因：{为什么不能绕过}
- 状态：⏳ 待修复 / ✅ 已修复
- 修复方式：{简述}

## 执行日志
- {YYYY-MM-DD HH:MM} — 🎯 目标接收，spec 创建
- {YYYY-MM-DD HH:MM} — 📋 场景判断：{场景}，flow：{flow}
- {YYYY-MM-DD HH:MM} — ▶️ 阶段 1 开始
- {YYYY-MM-DD HH:MM} — ✅ 阶段 1 完成
- ...
```

### 更新规则

- **实时更新** — 状态变化后立即 Write，不攒到阶段结束
- **阶段开始时** — 填入门禁、测试、验收标准
- **门禁通过时** — 勾选门禁项
- **测试编写/通过时** — 更新测试状态
- **验收通过时** — 勾选验收项
- **阶段完成时** — 标记阶段状态为 ✅，追加执行日志
- **发现阻塞 bug 时** — 立即追加到阻塞 Bug 区
- **目标达成时** — 更新元信息状态，追加最终日志

## Bug 分流细则

| 维度 | 阻塞级 | 非阻塞级 |
|------|--------|----------|
| 对当前阶段的影响 | 阶段无法继续 | 可以绕过，不影响推进 |
| 对核心功能的影响 | 核心功能无法工作 | 边缘 case、非核心路径 |
| 安全/数据风险 | 有数据丢失、安全漏洞风险 | 无实际风险 |
| 出现频率 | 必现或高概率 | 偶现、难以复现 |
| 处理方式 | 追加到 spec，TDD 解决 | 记入 `KNOWN_ISSUES.md` |
| 处理时机 | 立即，暂停当前阶段 | 目标达成后统一处理 |

**不可分流为「非阻塞」的情况：**
- 会导致测试失败（即使功能看起来正常）
- 会导致数据不一致
- 会影响后续阶段的实现基础

## 压缩恢复流程

```
⚠️ 如果发现上下文被压缩了（对话变短、之前的细节丢失）：

1. 第一时间读取 spec 文件
   Glob .tws/goal-specs/*.md → Read 找到的 spec 文件

2. 从 spec 中恢复：
   - 总体目标是什么？
   - 当前在哪个阶段？
   - 该阶段的验收标准完成了多少？
   - 有没有未解决的阻塞 Bug？

3. 读取 session 文件（辅助）
   Read .tws/sessions/{file}.md
   → 补充流程上下文（哪个 flow skill、走了什么路径）

4. 如果 spec 和 session 信息矛盾：
   → 以 spec 为准（spec 是用户视角的真相，session 是执行记录）

5. 确定下一步行动 → 继续执行

不要：
❌ 凭记忆恢复（压缩掉的正是记忆）
❌ 重新分析整个目标（spec 里已经有分析结论）
❌ 跳过压缩恢复直接问用户「我们到哪了」
```

## Skill 优先级

```
1. 用户明确指定的命令 — 最高优先级
2. using-tws-goal 目标驱动 — 次之
3. using-tws 场景路由 — 再次之（如果 goal mode 不适用）
4. 其他组件 skill — 按需调用
```

## 注意事项

- 第二步场景路由的判断逻辑与 `using-tws` 完全一致，确保两种入口的行为可预期
- Goal mode 下确认只有一次（第四步），此后全自动。如果确实遇到无法自行决策的分叉，停下来报告用户，不要硬猜
- spec 文件是 goal mode 的灵魂，宁可多写不要少写。spec 不清楚 = 目标不清楚
- 压缩恢复是 goal mode 的保命机制。如果压缩后没读 spec 就开始做事，等于蒙眼开车
- `KNOWN_ISSUES.md` 记录的非阻塞 bug 在目标达成时必须汇报，不能默默留着
- Goal mode 不等于可以跳过 reviewing — review 子 agent 仍然用干净上下文独立加载

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| 「这个目标很简单，不用写 spec 了」 | spec 不是写给复杂目标的，是写给会压缩的上下文的 |
| 「先做起来，spec 后面补」 | 「后面」= 永远不会。spec 是方向盘，不是行车记录仪 |
| 「这个 bug 看起来不严重，先不管」 | 不管 = 埋雷。分流是「记下来」，不是「忽略」 |
| 「压缩了也没事，我记得住」 | 压缩掉的正是你以为记得住的细节 |
| 「这个方案快一点，先这样吧」 | 快 = 下一次返工。根源解决才是真正的快 |
| 「验收标准都差不多，这步跳过吧」 | 跳过验收 = 盲飞。每步验收是唯一的进度锚点 |
| 「测试后面统一补」 | TDD 的核心是「先写测试」。统一补 = 不是 TDD |
| 「这个阶段很简单，合并到下一步吧」 | 合并 = 跳过检查点。每个阶段独立验证才有意义 |
