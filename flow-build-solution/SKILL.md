# 做方案

## 复杂度门禁（第 0 步）

```
检查条件：
□ 项目周期 ≤ 2 周？
□ 单一客户/单一场景？
□ 不涉及新架构设计？
□ 不涉及外包/分包协作？

全部满足 → 简化路径
任一不满足 → 完整路径
```

### 简化路径

```
需求澄清 → 方案设计（轻量）→ 报价（轻量）→ 展示材料（简化）
跳过：方案构思、方案评审、报价评审
```

### 完整路径

```
需求澄清 → 方案构思 → 方案设计 → 方案评审 → 报价 → 报价评审 → 展示材料
```

---

## 完整路径

### ① 需求澄清

主 agent 派子 agent 执行：

```
子 agent 通过 Skill 工具加载 comp-proposal-discovery，执行：
1. 整理客户原始需求（文字/语音/会议记录）
2. 识别显性需求和潜在需求
3. 明确：谁用？解决什么问题？期望的结果是什么？
4. 界定范围：做什么、不做什么
5. 输出：需求摘要 + 范围边界 + 关键约束
```

主 agent 验收：
- [ ] 需求是否有模糊地带？（有一句说不清楚的就追问）
- [ ] 范围边界是否明确？（"不做"比"要做"更重要）
- [ ] 关键约束是否列全？（时间/预算/技术栈/合规/依赖）

### ② 方案构思

主 agent 派子 agent 执行：

```
子 agent 通过 Skill 工具加载 comp-proposal-ideation，执行：
1. 多视角发散：至少从成本优先/风险优先/灵活优先 3 个角度探索解法
2. 假设映射：每种解法依赖的关键假设
3. 比较收敛：淘汰不合约束的思路，选出推荐方案
4. 输出：方案构思（推荐方案 + 淘汰理由 + 关键假设）
```

主 agent 验收：
- [ ] 是否探索了至少 3 个真正不同的方向？
- [ ] 淘汰理由是否绑定具体约束或假设？
- [ ] 推荐方案的假设数是否 ≤ 5 个？

> 方案构思的输出是方案设计的输入——设计师拿到的不再是裸需求，而是"为什么要这样做"的决策上下文。

### ③ 方案设计

主 agent 派子 agent 执行：

```
子 agent 通过 Skill 工具加载 comp-proposal-solution，执行：
1. 基于需求摘要 + 构思结论做技术方案设计（架构/模块/技术栈）
2. 拆解交付物和里程碑
3. 识别风险和假设
4. 输出：方案文档（含架构草图、模块清单、时间线、风险清单）
```

主 agent 验收：
- [ ] 方案是否回应了需求摘要中的所有要点？
- [ ] 方案是否对应了构思阶段的推荐方向？（偏离要有理由）
- [ ] 模块划分是否合理？有没有职责重叠或遗漏？
- [ ] 技术选型是否有依据？

### ④ 方案评审

主 agent 派独立子 agent 执行（干净上下文，不加载此前步骤的历史）：

```
子 agent 通过 Skill 工具加载 comp-proposal-solution-review，执行：
1. 检查方案完整性（是否回应了所有需求点）
2. 检查架构合理性（技术选型、模块边界、依赖关系）
3. 检查范围适当性（有没有过度设计或设计不足）
4. 风险扫描（技术风险、资源风险、进度风险）
5. 输出：评审意见 + 通过/需修改/阻塞
```

主 agent 验收：
- [ ] 评审结论明确（通过/需修改/阻塞）
- [ ] 如果是"需修改"：修改项是否具体可执行？
- [ ] 如果是"阻塞"：阻塞原因是否充分？

> 评审通过后锁定方案，后续报价基于此方案，不再回头改方案。若后续发现方案问题，回到此步骤重审。

### ⑤ 报价

主 agent 派子 agent 执行：

```
子 agent 通过 Skill 工具加载 comp-proposal-pricing，执行：
1. 基于锁定方案估算资源（人力/时间/硬件/第三方服务）
2. 选定定价模型（固定总价/人天/里程碑/其他）
3. 输出：报价方案（含资源估算明细、定价逻辑、付款节奏建议）
```

主 agent 验收：
- [ ] 资源估算是否与方案中的模块划分对应？
- [ ] 定价模型选择是否有理由？
- [ ] 假设是否明确标注？（如"假设第三方 API 不超量"）

### ⑥ 报价评审

主 agent 派独立子 agent 执行（干净上下文）：

```
子 agent 通过 Skill 工具加载 comp-proposal-pricing-review，执行：
1. 检查估算逻辑（人天/费用是否有依据，有无遗漏项）
2. 检查定价合理性（和方案范围是否匹配，有无明显偏高/偏低）
3. 检查假设可行性（定价所依赖的假设是否成立）
4. 输出：评审意见 + 通过/需调整/阻塞
```

主 agent 验收：
- [ ] 评审结论明确
- [ ] 调整项是否可执行？
- [ ] 最终报价是否经主 agent 确认？

### ⑦ 展示材料

主 agent 派子 agent 执行：

```
子 agent 通过 Skill 工具加载 comp-proposal-presentation，执行：
1. 基于方案文档生成 PPT 大纲（页面结构 + 每页核心信息）
2. 生成讲稿要点（每页一句话核心信息 + 过渡衔接）
3. 可选：Demo 脚本（如涉及演示）
4. 输出：展示材料文档
```

主 agent 验收：
- [ ] PPT 大纲是否覆盖方案核心要点？
- [ ] 叙事逻辑是否自洽？（问题 → 方案 → 报价 → 优势）
- [ ] 是否有面向客户视角的表达？（而非内部技术视角）

## 完成依据

- [ ] 需求摘要已确认
- [ ] 方案构思已完成
- [ ] 方案文档已完成
- [ ] 方案评审已通过（完整路径）
- [ ] 报价方案已完成
- [ ] 报价评审已通过（完整路径）
- [ ] 展示材料已完成
- [ ] 所有评审意见已处理
- [ ] .tws/sessions/{当前流程文件} 已删除

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| "这个客户很急，直接出方案和报价吧" | 急 = 更该审，出错了比不做更糟 |
| "方案很简单就不用构思和评审了" | 越简单的方案越容易漏东西。构思发现的问题比评审发现便宜 |
| "报价就是一拍脑袋的事" | 拍脑袋的报价回头看全是坑 |
| "PPT 随便做做就行" | 展示材料是客户对你方案的第一印象 |
| "需求和方案我一起出了" | 没澄清就设计 = 做的是自己的假设 |
| "评审过了就不用再看报价了" | 方案和报价是两个维度的风险 |
