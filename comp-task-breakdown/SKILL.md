# 任务分解

## 核心原则

**一个任务 = 一个可独立验证的原子操作。**

如果不能独立验证，说明拆得不够细。如果还要往下拆，说明拆得还不够小。

## The Gate Function

```
AFTER design doc is confirmed, BEFORE coding:

1. 按模块/功能点拆分
2. 对每个任务定义：
   - 描述（做什么）
   - 完成标准（什么算做完，必须可验证）
   - 验证方式（怎么验证，具体命令或步骤）
3. 输出任务列表
4. 用户确认
```

## 输出格式

```markdown
### 任务列表
- P-01：{描述}
  完成标准：{可验证的标准}
  验证方式：{具体方法}
  依赖：{依赖的任务，无则写「无」}

- P-02：{描述}
  完成标准：{可验证的标准}
  验证方式：{具体方法}
  依赖：{P-01}  ← 表示 P-01 完成后才能做 P-02
```

## 依赖规则

```
依赖 = 「这个任务开始前，必须先完成哪些任务」

- 有依赖的任务自动排在依赖任务之后执行
- 没有依赖的任务可以（在并发限制内）并行
- 依赖链不能成环（P-01→P-02→P-01 禁止）
- 如果检测到循环依赖 → 中止，重新调整任务划分
```

## 任务粒度分层

按改动规模选粒度，不强求 2-5 分钟：

| 类型 | 耗时 | 适用场景 |
|------|------|---------|
| 微任务 | 2-5 分钟 | 单文件、单函数、配置项改动 |
| 标准任务 | 10-20 分钟 | 2-3 个文件、涉及简单逻辑 |
| 复杂任务 | 30+ 分钟 | 跨模块改动、包含多个子步骤 |

**规则：**
- 复杂任务内部必须再拆子步骤（拆成微任务或标准任务的序列）
- 微任务不需要额外设计书，改动写在任务描述里即可
- 标准任务和复杂任务必须有独立的设计书

## 好任务 vs 坏任务

| 好任务 | 坏任务 |
|-------|-------|
| 「UserController 加 uploadAvatar 接口，返回 200 + url」 | 「优化一下」 |
| 「用户名校验：3-20 字符，只允许字母数字」 | 「完善功能」 |
| 「写单元测试覆盖：空值、超长、SQL 注入」 | 「补充测试」 |
| 「重构 auth 中间件，提取独立类」 | 「改代码」 |
| 「数据库加 user_avatars 表，含 user_id, url, created_at」 | 「加个表」 |

## 常见失败模式

| 表现 | 对策 |
|------|------|
| 任务描述模糊（"优化""完善"） | 拆到可验证为止 |
| 完成标准不可测（"看起来更好"） | 用具体指标替换 |
| 一个任务太大（"实现登录模块"） | 拆成多个子任务 |
| 没有验证方式 | 没想清楚怎么测就别拆 |

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| 「这个任务很简单，不用拆」 | 简单也拆。拆开才能验证每一步 |
| 「后面再做任务分解」 | 分解是编码的前提，不能跳过 |
| 「P-01 和 P-02 可以一起做」 | 那就说明拆错了。重新拆 |
| 「先写代码再补任务列表」 | 顺序错了。先计划再执行 |

## 为什么重要

- 没拆的任务 = 不知道要做多久、做完了没有
- 任务越模糊 → 偏差越大 → 返工概率越高
- 明确的任务标准 = 明确的验收依据 = 做完了就是做完了，不用猜
