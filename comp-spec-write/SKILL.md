# Goal Spec 编写

## 核心原则

**spec 写不清楚 = 目标不清楚。宁可多写，不可漏写。**

Goal spec 不是仪式性的文档骨架，而是后续所有实现阶段的唯一依据。子 agent 实现时只读 spec，不读设计书也不读调查结果。spec 里没写的 = 不会实现。

## Step 0: 理解上下文

在动笔之前，必须理解已有的全部信息：

```
1. 读取当前 spec 文件（Write 工具的目标路径）
   → 理解总体目标、约束条件、已有的阶段骨架
2. 读取主 agent 提供的调查/方案产出：
   → 设计书（design doc）
   → 任务分解（task breakdown）
   → 根因分析（root cause analysis）
   → 迁移计划（migration plan）
   → 方案构思结果（ideation results）
3. 通过 Skill 工具加载 found-tws-graph-usage
   → 用 tws-graph impact/calls/search 理解涉及模块的代码结构
4. 确认 spec 将要覆盖的范围边界（什么在范围内、什么明确不做）
```

不读完以上信息就动笔 = 写的 spec 跟实际情况脱节。

## The Gate Function

```
BEFORE writing the spec:

1. 确认已读完主 agent 提供的所有调查/方案产出
2. 确认理解：目标是什么、为什么要做、怎么做、边界在哪
3. 确认 spec 中每个阶段都在调查/方案产出中有依据

WHILE writing each section:

4. 总体目标必须拆解为以下 5 个子节，缺一不可：
   a. 问题背景 — 为什么需要做这个？现状有什么问题？
   b. 当前行为 — 现在系统/代码是什么样的？
   c. 期望行为 — 做完后应该是什么样的？
   d. 范围边界 — 明确在范围内（IN SCOPE）和不在范围内（OUT OF SCOPE）
   e. 成功指标 — 可量化的、可验证的完成标准（具体的命令/指标/数字）

5. 如有架构变更，必须写「总体架构设计」节，包含：
   a. 模块结构（目录树或模块列表）
   b. 关键接口/trait/签名（如果是代码项目）
   c. 数据流/调用链（从入口到出口的路径）

6. 每个阶段必须包含以下 4 个子节，缺一不可：
   a. 门禁 — 进入此阶段的前置条件（具体、可验证）
   b. 实现细节 — 要改哪些文件、怎么改、关键逻辑
   c. 测试 — 具名的测试用例列表（不是「测试功能正常」这种笼统描述）
   d. 验收标准 — 具体的、可量化的完成条件

7. 验收标准必须是「外部可观测的行为」或「可运行的命令输出」，不能是主观判断

AFTER writing:

8. 自检：拿 spec 给一个完全不了解这个任务的人看，他能知道每一步要做什么吗？
   如果不能 → 补足细节
9. 自检：每个验收标准是否可以由子 agent 独立验证（不需要问主 agent）？
   如果不能 → 改成可独立验证的表述
10. 用 Write 工具覆写 spec 文件
```

## Spec 质量标准

### 好 spec vs 坏 spec

| 维度 | 坏 spec（不可接受） | 好 spec（必须达到） |
|------|---------------------|---------------------|
| **总体目标** | 「给 export 加 --to 参数」 | 「用户需要反向追踪数据流来源。当前 export --from X 只能正向 BFS（X 调了谁），缺少反向遍历（谁调了 X）。需要新增 --to 参数，从目标节点沿入站边做反向 BFS」 |
| **成功指标** | 「功能正常工作」 | 「`tws-graph export mermaid --to META_TOOL_GUIDANCE -g` 输出包含反向调用链，且 `--from` 和 `--to` 同时指定时报错」 |
| **架构设计** | 「改 Rust 和 Python」 | 「修改 rust_core/src/export.rs 中 export_mermaid/export_dot 的函数签名（from_node: &str → from_node: Option<&str>，新增 to_node: Option<&str>），Python CLI 在 export 命令新增 --to 互斥参数」 |
| **测试用例** | 「测试功能」 | 「test_export_mermaid_reverse — 验证 to_node=Some("X") 沿 Inbound 边遍历；test_export_mutual_exclusion — 验证 --from 和 --to 同时指定时 panic」 |
| **验收标准** | 「CLI 能跑通」 | 「23 个 Rust 测试全 green；`tws-graph export mermaid --to <真实符号> -m -g` 输出正确反向图；`tws-graph export mermaid --from A --to B` 返回明确错误信息」 |
| **阶段实现细节** | 「修改 export.rs」 | 「修改 rust_core/src/export.rs:142-178 export_mermaid() 函数：参数签名改为 from_node: Option<&str>, to_node: Option<&str>；在函数开头新增互斥校验；BFS 遍历时根据 to_node 选择 Inbound/Outbound 方向」 |
| **范围边界** | 不写 | 「IN SCOPE: mermaid/dot/json 三种格式的反向遍历、--from 和 --to 互斥校验。OUT OF SCOPE: 可视化渲染方向调整、新导出格式支持」 |

### 深度自检清单

写完后逐项自问：

1. **总体目标** — 如果不读代码，只看 spec，能理解为什么要做这件事吗？
2. **架构设计** — 如果 spec 里有架构图/模块树/trait 定义，实现者还需要猜测结构吗？
3. **测试用例** — 每个测试有具体名称吗？测试覆盖了正常路径 + 边界条件 + 错误路径吗？
4. **验收标准** — 每个标准可以跑一条命令或看一个输出来验证吗？（不能是「代码质量好」这种）
5. **实现细节** — 子 agent 看了能直接开始写代码吗？还是需要再猜测具体改哪里？
6. **成功指标** — 有没有数字、命令输出、文件内容等客观证据？（不能是「感觉对了」）

## Spec 完整模板

以下是 spec 文件的完整模板。**每个 `{...}` 占位符旁边的 `<!-- 深度要求：... -->` 注释不可删除，必须满足其要求。**

```markdown

- 关联 flow：{flow-xxx}
- 关联 session：.tws/sessions/{file}.md
- 关联分支：{branch name}
- 目标状态：⏳ 进行中
- Spec 版本：v1（每次重新生成时递增）

## 总体目标

<!-- 深度要求：本节必须包含以下 5 个子节，每个子节至少 2-3 句 -->

### 问题背景
{为什么要做这个？现状有什么痛点？用户/系统的什么问题驱动了这个目标？}

### 当前行为
{现在系统/代码实际是什么样的？具体到文件路径、函数名、当前行为描述}

### 期望行为
{做完后系统/代码应该是什么样的？具体到行为变化、输出变化、接口变化}

### 范围边界
**IN SCOPE（在范围内）：**
- {具体要做的}
**OUT OF SCOPE（明确不做）：**
```

## 常见失败模式

| 表现 | 根本问题 | 正确做法 |
|------|---------|---------|
| 总体目标只有一句话 | 没拆解问题背景和期望行为 | 5 个子节每个至少 2-3 句 |
| 测试写「测试功能正常」 | 没有具体测试名称和场景 | 每个测试写明：测什么输入、期望什么输出 |
| 验收标准全是「能用」「通过」 | 主观判断代替可观测标准 | 每条验收 = 一个可运行的命令 + 期望输出 |
| 没有架构设计节 | 多个模块改动但没有整体视图 | 画出模块结构 + 关键接口 + 数据流 |
| 不写 OUT OF SCOPE | 范围边界模糊 | 明确列出不做什么 |
| 阶段只有门禁和测试，没有实现细节 | 以为子 agent 能自己推断怎么改 | 写到具体文件和行范围，子 agent 不需要猜 |
| 成功指标全是定性的 | 「更好」「更快」「更稳定」无法验证 | 换成「命令 X 输出包含 Y」「测试从 N 秒降到 M 秒」 |
| spec 复述用户原话但不展开 | 用户说「加个 --to 参数」spec 就写「加 --to 参数」 | 展开为：为什么需要、改哪里、怎么验证 |

## Rationalization Prevention

| 想说的话 | 真相 |
|---------|------|
| 「这个目标很简单，不需要写那么详细」 | spec 的读者不是现在的你，是上下文压缩后的主 agent 和没参与调查的子 agent |
| 「实现细节不用写，子 agent 自己会看代码」 | 子 agent 的上下文不包含调查过程。你看到的东西它看不到 |
| 「成功指标写『功能正常』就行，反正最后会验证」 | 「功能正常」不可验证。最后验证时会发现根本没标准 |
| 「架构设计就几个模块，不用画结构」 | 几个模块的组合方式就是 bug 的来源。不画出来 = 没想清楚 |
| 「测试名称无所谓，子 agent 自己起」 | 测试名称是 spec 的契约。spec 里写 test_export_reverse，子 agent 就必须实现它 |
| 「范围边界不用写，需求没说就是不做」 | 需求没说 ≠ 实现者不会做。不写 OUT OF SCOPE = 等实现者自由发挥 |
| 「这个 spec 模板太长了，我简化一下」 | 模板的长度 = 思考的深度。简化模板 = 简化思考 |
| 「用户原始需求很清楚了，照抄就行」 | 用户的"清楚"是对他自己而言的。spec 的工作是把隐性知识变成显性知识 |
